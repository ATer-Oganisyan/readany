# Задержки Android: книга из каталога и персонаж в тексте

Исследование 13 сентября 2026, `main` на `d87d9415`. Код приложения не менялся.

**Основная причина подтверждена CPU-профилями обоих действий:** изменение прогресса или времени открытия книги вызывает повторное сопоставление всего каталога с библиотекой в скрытых экранах Library и Search. Внутри многократно выполняется дорогое на данном Android `toLocaleLowerCase("ru-RU")`. Это блокирует JS-поток и задерживает показ нового экрана.

**Измерения**

Android Emulator API 36, ARM64, установленный dev-client `com.mishanaer.readany.dev`, Metro из текущего проекта, `dev=true`. Hermes runtime: OSS Release `250829098.0.16`, bytecode 98, Static Hermes. Подключение через штатный локальный CDP Metro. Использованы CPU sampler и существующий `__NARRA_PERF__` (проба каждые 50 мс), запись экрана через adb. Каталог по штатной диагностике: 1500 книг, фоновые запросы и очереди на момент контрольной проверки пусты.

| Действие | Окно измерения | Максимальная дополнительная задержка JS-таймера | Суммарное sampled self time в `toLocaleLowerCase` |
| --- | ---: | ---: | ---: |
| Открытие «Войны и мира» из каталога | 15,56 с | 3289 мс | 8102 мс |
| Нажатие на подчёркнутое имя в открытом тексте | 15,57 с | 3117 мс | 2617 мс |

Это один профиль каждого действия, не медиана и не P95. Время CPU суммировано по всем вызовам в окне; оно не равно времени до первой страницы. Максимальная пауза измерена таймером, не GPU/FPS. Сам профилировщик и dev-режим добавляют накладные расходы.

При открытии книги зафиксированы три длинные паузы: около 3226, 3289 и 3070 мс. Стек горячих вызовов:

```
LibraryScreenContent / SearchContent
  useMemo
    findReadableLibraryBookForCatalogBook
      bookIdentity
        normalize
          String.prototype.toLocaleLowerCase
```

Нативные locale-вызовы в первом профиле занимают примерно 4,18 с со стороны Library и 3,92 с со стороны Search. Во втором профиле тот же стек воспроизводится при открытии персонажа. Карточка в записи экрана отображается без портрета: SVG-размытие не нужно для воспроизведения этой задержки. За окна были зафиксированы 222 и 74 рендера карточек каталога соответственно; это не число полных пересчётов каталога.

**Почему разница с iOS возможна при одном коде**

В самом Android runtime отдельно выполнено по 2000 преобразований четырёх русских названий/имён, три серии, без CPU sampler:

| Вызов | Время 2000 вызовов, три серии |
| --- | --- |
| `toLowerCase()` | 2,11 / 2,01 / 2,48 мс |
| `toLocaleLowerCase("ru-RU")` | 858,86 / 863,51 / 849,19 мс |
| `toLocaleLowerCase()` | 5,37 / 5,01 / 5,02 мс |

Таким образом, на этом Android явная локаль стоит примерно в 340–430 раз дороже обычного lowercase. Это сравнение двух методов **внутри Android**, не измеренное соотношение Android/iOS. Результат на четырёх строках не доказывает полную семантическую эквивалентность для всех названий каталога.

Hermes использует платформенные средства интернационализации; реализации iOS и Android различаются, поэтому одинаковый JS не гарантирует одинаковую стоимость таких вызовов. Это документировано в [Hermes Intl](https://github.com/facebook/hermes/blob/static_h/doc/IntlAPIs.md). Историческое [обсуждение разработчиков Hermes](https://github.com/facebook/hermes/discussions/1211) описывает отдельные реализации и вызовы Java на Android; оно служит объяснением устройства, а не доказательством точного внутреннего пути текущего бинарника.

Парный замер на iOS в этой сессии не выполнялся. Пользователь сообщает, что там задержка не ощущается. В старом [отчёте от 28 августа](./search-freezes-summary-2026-08-28.md) измерялись iOS Simulator, каталог из 268 книг и переключения вкладок/подборок. Сегодняшний каталог из 1500 книг примерно в 5,6 раза больше. Старые результаты не проверяли ни этот объём, ни Android, ни открытие персонажа после записи прогресса.

**Точная цепочка в коде**

- При открытии Reader записывает `lastOpenedAt`: `packages/app-expo/src/screens/ReaderScreen.tsx:1745`. Сохранение позиции затем также вызывает `updateBook`: строки 659 и 1256; первый вызов throttle проходит сразу.
- При тапе персонажа `publishCharacterProgress` вызывается перед `navigate`: тот же файл, строки 666–674 и 1363–1372. Актуальный прогресс нужен, чтобы только что встреченный герой не оказался заблокирован.
- `packages/app-expo/src/stores/library-store.ts:1180` каждый раз создаёт новый массив `books` и новый объект книги, даже при одинаковых `progress/currentCfi`.
- `LibraryScreen.tsx:483` и `SearchScreen.tsx:117` зависят от всего массива `books` и повторно проходят весь каталог. Они продолжают вычисляться, находясь под читалкой/профилем. `memo` не отключает собственную подписку экрана на Zustand.
- `packages/app-expo/src/lib/narra/backend-catalog-library.ts:28`: после поиска точного edition ID для каждой оставшейся книги вычисляется текстовый ключ и ищутся старые локальные копии. Ключ каталожной книги вычисляется даже при отсутствии кандидатов старого формата.
- `packages/app-expo/src/lib/book/book-identity.ts:8`: название и автор каждый раз проходят `toLocaleLowerCase("ru-RU")`. При вложенном переборе повторно нормализуются те же локальные названия.
- Проверки фокуса Library/Search ограничивают загрузки и жесты, но не эти вычисления. Аналогичный проход есть в категории и поисковой выдаче.

Обновление store синхронно уведомляет подписчиков до `navigate`. Сам тяжёлый React-пересчёт может быть запланирован после callback; нельзя утверждать, что все секунды проведены внутри `updateBook`. Профили подтверждают, что пересчёт занимает общий JS-поток в момент перехода.

**Другие проверенные кандидаты**

Android DEV сначала пробует native Lighttpd (таймаут запуска 5 с), iOS DEV сразу TCP. Проверки здоровья сервера имеют предел 1,5 с. Эти числа являются пределами ожидания, не обязательными задержками. В сохранённом профиле нет подтверждения, что native timeout стал причиной наблюдаемой паузы.

Каждое новое открытие создаёт WebView, повторяет EPUB-разбор и прогрев четырёх начертаний шрифта с пределом 750 мс. Это может добавлять время до текста, но не объясняет общий найденный стек книги и персонажа. Обычный EPUB-путь передаёт URL локального сервера, не всю книгу через base64.

`ReaderCharacterCard.tsx:127` использует полноразмерное SVG-размытие и маску. В Android реализации `react-native-svg` фильтр выполняется в пути `onDraw` и может ухудшать анимацию карточек с портретом. Это вторичный кандидат, который требует отдельного native trace после устранения JS-пауз. Видео у профиля выключено через `staticPortraitOnly`.

**Приоритет исправления**

1. Перестать пересчитывать соответствия каталога из-за `progress`, `currentCfi` и `lastOpenedAt`. Индекс сопоставления должен зависеть от состава/идентичности/доступности книг, а не от позиции чтения. Результаты лучше хранить как ID, чтобы не возвращать устаревшие объекты Book.
2. Строить один общий индекс edition ID и однозначных legacy-ключей вместо многократного вложенного прохода. Без legacy-кандидатов не нормализовать каталог. Сохранить правило неоднозначности старых копий.
3. Пропускать `updateBook` без фактических изменений. Проверить возможность `toLowerCase()` для внутренних ключей с тестами совместимости; простой перенос на locale-default сделает результат зависимым от языка устройства.
4. Сохранить публикацию прогресса перед профилем героя. Не устранять её удалением: это вернёт прежнюю ошибку доступа к персонажу.
5. Повторить оба сценария с тёплыми/холодными открытиями, большой библиотекой и каталогом, затем парно iOS/Android и Android release. Отдельно измерять tap → первый кадр → готовый текст/карточка, JS stalls и native UI rendering.

React Native отдельно предупреждает, что dev-режим замедляет JS, а занятый JS-поток задерживает обработку касаний: [Performance Overview](https://reactnative.dev/docs/performance). Dev-режим влияет на абсолютные цифры, но не устраняет обнаруженную лишнюю работу.

## Исправление и проверка после исследования

В той же рабочей копии устранён подтверждённый источник затрат:

- Общий индекс библиотечных edition ID и однозначных legacy-ключей вместо вложенных проходов. Сопоставления переиспользуются при изменении прогресса/CFI/времени открытия; возвращаемые объекты Book всегда берутся из актуального массива.
- Индекс обновляется при изменении состава, названия, автора, edition ID, формата, доступности или удаления книги. Кэш использует WeakMap, не накапливает все исторические массивы библиотеки.
- Для внутренних ключей используется `toLowerCase()` вместо дорогого явного `ru-RU`. Проверены русские названия, ё/е, пробелы и примеры Unicode на совместимость с прежней нормализацией.
- `updateBook` не уведомляет подписчиков и не пишет на диск при неизменившихся значениях. Новый прогресс по-прежнему публикуется синхронно перед навигацией к герою.

Повторено открытие той же книги и того же имени на Android dev-client с теми же CPU sampler и 50-мс пробой:

| Сценарий | Максимальная пауза до | После |
| --- | ---: | ---: |
| Книга из каталога | 3289 мс | 1560 мс |
| Персонаж в тексте | 3117 мс | 240 мс |

Горячий стек нормализации каталогов исчез. Суммарное sampled self time всех `toLocaleLowerCase` в окне книги уменьшилось с 8102 до 12,8 мс (оставшиеся вызовы в других местах приложения); в окне персонажа — с 2617 до 0 мс. При тапе персонажа больше нет рендеров каталожных карточек в диагностике. В окне книги остаются другие затраты React/инициализации читалки: оставшиеся 1560 мс не следует считать устранёнными.

Это по-прежнему одиночные DEV-профили, не серия и не полное время до первого кадра. Прогретость процессов между измерениями могла различаться. iOS и release после изменения не измерялись.

Прошли 82 теста в 9 файлах: сопоставления, кеширование на 1500 книгах, инвалидирование после изменения/удаления/дубликатов, поиск, импорт, публикация прогресса и доступ к персонажам. `tsc --noEmit` прошёл. Biome прошёл для новых/изменённых файлов; для store проверка выполнена с отключённой сортировкой импортов, поскольку существующий порядок не менялся. `git diff --check` прошёл. Книга визуально открылась на сохранённой странице; карточка персонажа показала имя и биографию. Нативная пересборка не выполнялась.

Артефакты после изменения: `/tmp/narra-book-fixed.json`, `/tmp/narra-character-fixed.json`, соответствующие `.mp4`.

Контрольное повторное открытие того же персонажа без CPU sampler завершилось успешно: максимум дополнительной JS-паузы 177 мс за окно 5,18 с, рендеров каталога нет. Результат: `/tmp/narra-character-fixed-unprofiled.json`. Это дополнительная проверка после исправления, не парное сравнение с исходным непрофилированным запуском (он ранее прервался).
