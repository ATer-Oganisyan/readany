# Задержка при возврате в Library: покадровый разбор

Источник: `/Users/manaer/Downloads/IMG_3768.MP4`, 1 октября 2026 года. Запись физического телефона с TestFlight. Исследован текущий код `240f6ba` с локальными изменениями. Через плагин Expo проверена последняя production-сборка: `1.4.0 (113)`, EAS build `02401ed5-75f7-4745-836e-3109ef8eab34`, git metadata `240f6ba3769c4d322ade33884dc6a780a9c9b21b`. Номер сборки на самом видео не виден. Git metadata EAS не доказывает совпадение незакоммиченных файлов, попавших в архив, с текущим checkout.

## Уточнение, определяющее дальнейшую проверку

Пользователь подтвердил три условия:

- Пауза при переключении на Library возникает с активным **Popular**; с **My books** её нет.
- То же различие наблюдается при закрытии reader.
- Пауза появляется или усиливается после прокрутки Popular.

Общий подозреваемый — повторный показ страницы Popular. Загрузка книги, обработчик крестика и общий tab navigator сами по себе не объясняют все три условия. Нативный zoom может давать отдельные задержки, но теперь это вторичная гипотеза, а не установленная причина этих двух симптомов.

На двух других переходах в этой записи — Chats → Profile и Profile → Chats — смена содержимого и начало изменения выделения впервые видны в одном кадре. Это сравнительное наблюдение, а не статистика скорости: есть пропуски временных интервалов между кадрами и всего по одному переходу.

Важная граница измерения: видео не показывает палец, touchDown и touchUp. Подсветка/растяжение стеклянного индикатора может отражать удерживаемое касание. Предварительную формулировку «задержка подтверждена» следует понимать только как подтверждение визуального рассогласования.

Пользователь уточнил: палец быстро отпускает, вкладку не удерживает. Это делает объяснение длительным удержанием маловероятным и подтверждает пользовательский сценарий быстрого тапа. Точный интервал от touchUp по-прежнему не измерен; 356,7 мс — интервал от видимой подсветки.

## Проверка текущего кода

- `TabNavigator.tsx` использует нативный tab navigator. В установленном `react-native-screens` методы `RNSTabBarController.shouldSelectTab` / `didSelectTab` разрешают обычный выбор в UIKit и затем сообщают результат в JS. В приложении не включён запрет нативного выбора. Ожидания ответа JS перед разрешением выбора здесь нет.
- Уже показанная вкладка сохраняется. Повторное открытие Library не означает обязательное создание всего экрана с нуля.
- Основной контент Library не подписан напрямую на `useIsFocused`. Фокус обрабатывает отдельный `LibraryCatalogLifecycle`: активность каталога, swipe guard, окно видимых и соседних обложек. Загрузка сети не ожидается перед показом вкладки.
- Тесты неизменившихся карточек при смене фокуса проходят. Это исключает проверенный сценарий лишнего React-рендера, но не измеряет стоимость нативной раскладки и отрисовки.
- Явного таймера задержки перехода в Library в рассмотренной цепочке нет. Отрисовка сетки/теней и работа UIKit остаются гипотезами до профиля; по одному видео выбрать между ними нельзя.

## Отдельно: крестик reader

`ReaderScreen.closeReader` вызывает подготовку возврата zoom и `navigation.goBack()` без ожидания сети или сохранения. Таймер 1200 мс в `sheet-zoom-return.ts` восстанавливает тень как запасной путь; он не откладывает закрытие книги. Нативный zoom выполняет раскладку и восстановление clipping. Задержку этой цепочки на присланном видео измерить нельзя: закрытия reader в нём нет.

## Что удалось проверить в работающем приложении

Dev-client build 36, Simulator iPhone 17 Pro / iOS 26.5, текущий JS через Metro. Нативная пересборка не выполнялась. Первоначальный тайм-аут JS-пробы был временным: после загрузки runtime подключение заработало.

В прогретом каталоге загружены метаданные 1500 книг. При исследованных повторных переходах очередь обложек была пуста; счётчики `catalog.card` / `catalog.perspective` и события загрузки обложек не увеличивались. Закрытие reader в Popular также не вызвало рендера карточек. Это не подтверждает гипотезу повторного построения каталога в JS для этих локальных переходов.

Через React DevTools hook прочитано фактическое дерево Library, включая скрытую страницу My books. Затем выполнено пять свайпов вниз в Popular и возврат к началу списка:

| Компоненты в дереве Library | До прокрутки | После прокрутки и возврата наверх |
| --- | ---: | ---: |
| `CatalogBookCard` | 20 | 70 |
| `BookCard` из My books | 10 | 10 |
| `LinearGradient` | 48 | 186 |
| `RCTView` | 444 | 1036 |
| `RCTImageView` | 26 | 72 |

Это количество компонентов React, не измерение потребления памяти в байтах и не число видимых карточек. На экране по-прежнему только несколько книг. После переключения внутреннего раздела на My books все 70 карточек Popular и 186 градиентов остаются в React-дереве; очереди каталога становятся неактивными.

Механизм найден в `LibraryScreen.tsx`: `catalogChunkCount` начинается с 10, эффект поднимает его до размера экрана с запасом (на этом устройстве 20), затем только увеличивает. `catalogBooks.slice(0, catalogChunkCount)` отрисовывается через `.map()` внутри обычного `ScrollView`. Верхняя граница ограничена лишь длиной каталога. Это постепенное создание всего пройденного префикса, а не ограниченное окно видимых карточек.

Есть и отличие в оформлении: готовая `CatalogBookCard` включает `BookSurfaceEffects` с тремя `LinearGradient` и внутренними тенями. `BookCard` из My books передаёт `coverEffects={false}` и использует `BookSpineOverlay`. Установленный `expo-linear-gradient` при `LinearGradientLayer.display()` создаёт bitmap через `UIGraphicsBeginImageContextWithOptions`; это нативная работа, которую счётчики React-рендеров не показывают.

### Ограничения профиля и важный отрицательный результат

Сняты профили главного потока утилитой `sample` и локальные JS-пробы. В одном возврате Popular до прокрутки `LinearGradientLayer.display()` попал в 66 семплов, после прокрутки — в 254. Однако в контрольном возврате **My books после той же прокрутки** он попал в 503 семпла. Поэтому нельзя утверждать, что наличие градиентов или их суммарная стоимость уже объяснили задержку только Popular. Требуется привязка работы к первому показанному кадру: агрегированный профиль не разделяет работу до и после него.

В обеих сравниваемых пробах после прокрутки — ноль рендеров карточек и ноль событий загрузки обложек. Максимальная задержка 50-мс JS-таймера в этих коротких окнах была около 122 мс для Popular и 70 мс для My books. **Это не задержка касания, не FPS и не измерение TestFlight на телефоне.** Профили включают работу accessibility при снятии UI-состояния, которую также нельзя приписывать обычному пользовательскому переходу. Продолжительность вызова UI-инструмента и его тайм-аут ожидания стабильности не являются временем переключения приложения.

Артефакты диагностики в `/tmp`:

- `narra-popular-return-paired.json`, `narra-popular-reader-dismiss.json` — прогретые переходы до длинной прокрутки.
- `narra-library-after-scroll-counts.json` — состав дерева после прокрутки.
- `narra-popular-after-scroll-return.json`, `narra-mybooks-after-scroll-return.json` — сравнение двух внутренних разделов после прокрутки.
- Одноимённые `*.sample.txt` для переходов после прокрутки — нативные профили одинаковой длительности, 12 секунд.

Физический телефон обнаружен на USB, но CoreDevice сообщает `unavailable`, запрос процессов завершается ошибкой 4016. Предпочтительный DDI отмечен как совместимый и пригодный, поэтому несовпадение номера Xcode и iOS само по себе не объявляется причиной. Нативный профиль пользовательского TestFlight на телефоне не получен.

## Вывод и минимальный план

**Подтверждено:** после прокрутки Popular не освобождает созданные карточки и сильно увеличивает дерево интерфейса. Старое исправление уменьшает начальную нагрузку, но не ограничивает её после длительной прокрутки. Это согласуется с уточнениями пользователя и остаётся главным кандидатом для следующего контролируемого опыта. **Не доказано:** какая конкретно операция задерживает первый кадр Popular и начало закрытия reader на физическом телефоне.

1. На одинаково прогретых данных сравнить текущий Popular после длинной прокрутки с временно ограниченным числом карточек. Одинаковые книга, позиция списка и способ возврата; измерять touchUp → первый кадр отдельно для таббара и крестика. Сохранить оформление карточек, чтобы менять только один фактор.
2. Если ограничение устраняет обе паузы, заменить растущий префикс ограниченным окном карточек, сохраняя кеш обложек, позицию прокрутки и карточку назначения zoom. Не сокращать список сбросом на каждом фокусе: это создаст повторные монтирования и может потерять цель перехода.
3. Если пауза останется, отдельно проверить повторное появление страницы `PagerView` и эффекты обложек. Менять глобальный навигатор, добавлять таймеры или новый кеш без этого сравнения оснований нет.

[Expo документирует задержку zoom-переходов](https://docs.expo.dev/router/advanced/zoom-transition/#known-limitations), особенно при быстрых повторных открытиях/закрытиях. Но обе страницы используют общую навигацию, а пользовательская разница связана с Popular и прокруткой. Этот известный дефект не доказан как основная причина здесь; переносить сторонний патч zoom без проверки соответствия сценария нельзя.

## Внесённое исправление и проверка

После разрешения пользователя внесено ограниченное окно карточек Popular: видимая область и запас по три ряда с каждой стороны. Пройденные строки заменяются равными по высоте отступами. Существующие ScrollView, горизонтальный pager, постепенное расширение каталога и кеш файлов обложек сохранены. Замена всего экрана на новый список не потребовалась.

Позиция сетки измеряется относительно внутреннего контейнера ScrollView; это учитывает переключатель разделов и элементы над сеткой. Окно загрузки обложек использует тот же расчёт. Завершённое появление обложки запоминается по стабильному объекту метаданных и URI через WeakMap: при возвращении к карточке анимация не повторяется, при замене URI или ошибке декодирования снова требуется загрузка. Кеш изображений не дублируется.

Сравнение в том же Simulator после пяти длинных свайпов:

| Показатель | До ограничения | После ограничения |
| --- | ---: | ---: |
| Смонтированные карточки Popular | 70 | 20 |
| LinearGradient в Library | 186 | 60 |
| RCTView в Library | 1036 | 436 |

После исправления на шагах 1–5 число карточек оставалось равным 20, хотя доступный префикс вырос с 30 до 70 книг. После возврата наверх осталось 12 карточек, 36 градиентов и 340 RCTView. Кеш загруженных обложек сохранился; в момент проверки очередь загрузок пуста. Исходные числа описывают конкретные прогретые данные, а не универсальный предел для всех размеров экрана.

Проверены в UI:

- Profile → Popular после длинной прокрутки: offset `7141` и видимые книги сохранились.
- Popular → My books → Popular, возврат наверх по повторному тапу Library: содержимое и обложки отображаются без пустого участка.
- Открытие «Тараса Бульбы» из середины Popular и закрытие крестиком: offset остался `2849`; все 20 идентификаторов источников zoom сохранились, включая `catalog:eval-v14-taras-bulba:_r_51_`. Целевая карточка не размонтировалась во время чтения.

Проверки кода: 57 тестов в пяти файлах (геометрия окна, повторное появление обложки, существующие сценарии каталога/поиска и cover store), TypeScript, Biome для шести затронутых файлов, `git diff --check`.

**Граница результата:** устранён подтверждённый неограниченный рост дерева Popular. Задержка touchUp → первый кадр на физическом телефоне после исправления ещё не измерена; исчезновение обеих пользовательских пауз требует проверки на телефоне. Поворот устройства при открытом ридере не проверен. Нативная сборка не запускалась, в TestFlight исправление не опубликовано; текущий JS доступен в работающем Simulator.

Во время первоначальной отладки возник один crash Hermes Debugger (`CodeBlock::getSourceLocation`), сохранённый в `~/Library/Logs/DiagnosticReports/Narra-2026-10-01-140915.ips`. После исправления передачи native ref для измерения и полного перезапуска описанные сценарии прошли без повторного падения. Причинная связь crash с измерением не установлена; это не профиль release-сборки.
