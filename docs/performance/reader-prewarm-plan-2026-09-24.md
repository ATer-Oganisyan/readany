# Открытие книги: план ускорения и проверка архитектуры

24 сентября 2026. План для текущего рабочего дерева, включая уже существующие незакоммиченные изменения. Код приложения в рамках этой проверки не менялся. Добавлен только воспроизводимый браузерный замер.

## Решение

Сначала устранить лишние ожидания и работу при открытии. Затем проверить предварительную загрузку пустой оболочки ридера штатным `navigation.preload`. Переносить одну постоянную WebView между нативными экранами стоит только после измерения дополнительной пользы и проверки нативного прототипа.

Желаемый результат: к нажатию на книгу движок и фиксированные шрифты готовы; после нажатия остаются получение файла и построение нужной страницы. Скачивание новой книги остаётся отдельной затратой. При ошибке шрифта книга не должна бесконечно оставаться под загрузчиком.

**Важная поправка к первоначальной идее:** iOS уже использует общий `WKProcessPool`. Сейчас повторяются создание представления, загрузка HTML/JS и подготовка документа. «Один процесс WebKit» и «один экземпляр WebView» — разные вещи. Обычный `goBack` удаляет Reader из стека; ссылка `ref`, `memo` или `freezeOnBlur` не сохранят его WebView после удаления.

## План внедрения

### 1. Снять исходные показатели открытия

Использовать существующие `recordDiagnostic` и performance probe, без нового сервиса аналитики. Добавить недостающие отметки в общий путь открытия и Reader: нажатие, файл готов, WebView ready, начало `openBook`, готовность шрифтов, нужная позиция построена, загрузчик снят и текст показан. Для входов из каталога, заметок и чатов тоже нужна исходная отметка нажатия.

`reader_open` сейчас пишется уже после `webViewReady`, поэтому разность `reader_loaded − reader_open` не измеряет всё открытие. Время внутри RN и WebView считать отдельно собственными монотонными часами; не вычитать их несогласованные `performance.now()` друг из друга. Сквозное время считать на RN-стороне при получении событий. Новые разрешённые поля добавить в существующий whitelist диагностического журнала; текст книги не логировать.

Измерять отдельно:

- **Нажатие → видимая правильная страница**, со снятым загрузчиком; `loaded` сам по себе ещё не доказывает показ кадра.
- **Первый жест → перелистывание**, а также паузы RN JS и WebView: это разные потоки.
- Память приложения вместе с процессом web content до прогрева, после него и после серии открытий.

До/после: одинаковая сборка и устройство, без CPU sampler, одинаковые книги, позиции и настройки. Не смешивать debug iOS с JS TCP-сервером и production с native-сервером. Минимум 20 тёплых открытий каждого сценария, отдельно 5 холодных; медиана, p95 для тёплых серий, максимум паузы. Для коротких холодных серий показать все результаты.

Сценарии: локальная EPUB, повторное открытие той же книги, другая книга, вход по цитате, книга с большой главой, PDF, новая книга из каталога, открытие сразу после запуска приложения и после возврата из фона.

### 2. Убрать подтверждённую лишнюю работу

**Шрифты.** Сохранить существующий фиксированный SB Serif и четыре его начертания. Загружать их заранее в документ ридера после получения CSS/адреса локального сервера. Запоминать успешный прогрев для актуального источника; после смены адреса сервера или пересоздания документа проверять заново. Не считать неудачный прогрев вечным успехом.

Заменить неограниченное ожидание всех `doc.fonts.ready` на ограниченную проверку нужных шрифтов видимой секции и стабильной раскладки. Начать с существующего бюджета 750 мс **для ожидания шрифтов в целом**, а не двух последовательных ожиданий по 750 мс. При ошибке/истечении срока показать читаемую страницу с согласованным fallback, восстановить целевую позицию и не допустить поздней незаметной смены шрифта с перескоком страницы. Fallback удерживать для текущего открытия; следующая попытка открытия может восстановить основной шрифт. Подтвердить поведение экспериментом: `font-display: swap` само по себе не гарантирует стабильную пагинацию.

Это не лимит всего открытия: чтение файла и построение страницы остаются. Просто удалить `await doc.fonts.ready` нельзя — загрузчик исчезнет раньше, но положение текста может измениться.

**Asset.** Убрать `readerHtmlUri` из причины повторного запуска эффекта, сохранив проверку целостности и существующий путь восстановления отсутствующего/испорченного файла. Не добавлять бессрочный кеш, скрывающий удалённый файл.

**Таймер.** Подписать ReaderContent на булево условие достижения порога чтения вместо количества миллисекунд; сохранить текущую защиту от повторной отправки события. Показатели чтения продолжают обновляться, но этот счётчик перестаёт перерисовывать экран каждую секунду.

**Цитата.** При первом открытии выбирать `route.cfi` раньше сохранённой позиции. Проверку сохранённого CFI по `book.progress` применять только к восстановлению прежнего места: иначе она отправит читателя обратно с явно выбранной цитаты. Поздний эффект оставить для нового перехода внутри уже открытой книги; начальный переход не повторять. При неверном CFI оставить существующий разумный fallback.

Основные файлы: `ReaderScreen.tsx`, `reader.template.html`; пересобрать `reader.html` штатным `pnpm build:reader`. Это JS/asset-изменения, нативная пересборка для них не нужна.

**Проверка этапа:** замедленный/ошибочный ответ шрифта не оставляет вечный загрузчик; обычный шрифт не меняет страницу после показа; подготовка asset вызывается один раз; цитата открывается сразу на целевой позиции; библиотечный прогресс и телеметрия сохраняются.

### 3. Проверить самый дешёвый прогрев настоящей WebView

Сначала маленький прототип `navigation.preload` для пустого Reader, до большого рефакторинга. Официальный API монтирует экран заранее, но этого недостаточно: текущая iOS-реализация WebView создаёт WKWebView только после подключения к окну.

Три независимых признака успеха: **React-компонент смонтирован → HTML прислал `ready` до нажатия → четыре шрифта готовы до нажатия**. Проверить на iOS и Android. Счётчик/идентификатор документа должен остаться тем же после `navigate`; после закрытия и подготовки следующего Reader он должен измениться.

Для прототипа нужна пустая оболочка с WebView. Передача пустого bookId текущему Reader недостаточна: при отсутствии книги он возвращает `ReaderLoadingChrome`, где WebView вообще нет. Текущий `applySettings` тоже не запускает прогрев шрифтов без книги — добавить короткую команду подготовки, вызывающую существующую функцию warmup после установки CSS.

Если все три признака подтверждены, внедрять так:

1. WebView и её транспорт принадлежат стабильной оболочке маршрута Reader. Книга, её панели, подписки и сессия чтения монтируются отдельно после появления реального запроса. Оболочка сохраняет состояние `ready`/готовности шрифтов и передаёт его подключившейся сессии: одноразовый `ready` может прийти до её появления. Ожидать второго события нельзя — книга зависнет. При пересоздании документа готовность сбрасывается.
2. Оболочка существует уже во время скачивания каталожной книги и сохраняется при переходе от загрузчика к тексту; не менять её `key` при появлении bookId. Загрузка файла и подготовка движка могут идти параллельно.
3. Вызывать preload одного пустого Reader после того, как библиотека стала интерактивной. После полного закрытия Reader готовить следующий. Во время активного ридера второй не создавать; после ухода приложения в фон новую подготовку не начинать.
4. При нажатии использовать обычный `navigate('Reader', параметры)`. Существующие импорт, проверка файла, отмена загрузки, native zoom, возврат к карточке и нативные шторки должны сохраниться.
5. Если пользователь нажал до окончания прогрева, использовать тот же экземпляр и обычное ожидание готовности. Ошибка прогрева не блокирует библиотеку; штатный retry сохраняется.

Параметры пустого Reader должны явно отличаться от запроса книги; не подставлять фиктивный bookId и не запускать на скрытом экране импорт, `lastOpenedAt`, reading session, TTS, аналитику открытия или book-specific запросы. Чтение параметров в `RootNavigator` должно учитывать пустую оболочку. До фокуса preload не должен вызывать запрещённые для него действия навигации/`setOptions`.

Это заранее подготовленный следующий экземпляр, а не один вечный экземпляр на всё приложение. Он решает ту же пользовательскую задачу — убрать подготовку движка из пути после нажатия — с меньшим объёмом изменения жизненного цикла книг.

**Условие остановки:** если скрытый preload не получает `ready`/готовность шрифтов, он не решает задачу прогрева движка. Не выдавать React mount за ускорение. Тогда оставить исправления этапа 2 и перейти к оценке этапа 4, не наращивать custom router вокруг неработающего подхода.

### 4. Если нужен именно один постоянный экземпляр

Этот вариант пока не подтверждён нативным прототипом. Обычный JS singleton/ref, портал над корневой навигацией или `cacheEnabled` недостаточны. Root overlay не гарантирует правильное отображение поверх отдельного нативного modal-контроллера. Возврат показанного экрана в `preloadedRoutes` тоже не штатное решение: native-stack запрещает обратный переход `activityState` с 2 на 0.

Сначала отдельный прототип владения WebView на iOS/Android: один нативный экземпляр живёт дольше временного Reader-экрана, корректно показывается/скрывается в его контейнере, сохраняет bridge, размер, ввод и zoom. Проверить, что Fabric recycle не уничтожает его и не оставляет старый обработчик событий. Это уже работа с нативным жизненным циклом; реализацию и стоимость нельзя считать установленными одним анализом JS-кода. Не менять текущую навигацию всех экранов ради экономии, ещё не измеренной на устройстве.

До подключения реальных книг сделать безопасным сам `openBook`:

1. Уникальный токен каждого открытия, включая A → закрыть → A. Текущий `bookId:filePath:attempt` для этого не подходит.
2. После каждого асинхронного шага проверять захваченный токен; позднее завершение A не может заменить B. Не подставлять глобальный текущий ID в старый callback: это ошибочно выдаст старый ответ за новый.
3. При закрытии остановить текущую работу, `view.close/remove`, затем `book.destroy?.()`. Текущий Foliate `view.close` не освобождает саму книгу; EPUB/PDF имеют собственный `destroy`. Освободить также книгу, которую закончила создавать уже отменённая операция.
4. Сбросить выделения, поиск, ruby-mode, персонажей, сцены, TTS-подсветку, выделенный текст и таймеры. Общие движки, успешно загруженные шрифты и словари можно сохранить. Не вводить кеш распарсенных книг.
5. Начальные book-specific данные передавать с `openBook` после reset. Сейчас эффекты персонажей/сцен идут раньше открытия: простой reset сотрёт данные новой книги.
6. Защитить токеном команды и события TOC/selection/search/scene/translation/TTS; завершать старые ожидающие bridge-запросы при отсоединении сессии. Старые RN-таймеры ruby/подсветки тоже не должны воздействовать на новую книгу.
7. Сохранить lifecycle RN-сессии конкретной книги: немедленная запись позиции при закрытии, завершение чтения, корректное продолжение аудио, отмена загрузок. Обезвредить отложенную `throttledSaveProgress` завершённой сессии: у текущего throttle есть trailing timer без `cancel/flush`, и старая запись может затереть финальную или новую позицию после A → B → A. Это включить в тот же интеграционный сценарий. Проще сохранять только оболочку, а не весь ReaderContent вместе с его book-specific хуками.
8. При уничтожении web content системой или смене источника assets восстановить оболочку и текущую позицию существующим recovery-путём. «Один раз» означает до уничтожения процесса, а не гарантию на весь срок работы приложения.

Один интеграционный сценарий должен покрыть A → B → A с искусственно задержанным первым A: активна последняя A, чужие события/команды отброшены, старые книги получили `destroy`, прогресс записан раздельно. Затем проверить EPUB ↔ PDF, ruby on → off, поиск/заметки/сноски, восстановление перевода, аудио и смену localhost-адреса.

**Условие включения:** доказанное улучшение полного открытия на устройстве после этапов 2–3, сохранённая навигация и память без роста от количества ранее открытых книг. Если выигрыш укладывается в шум измерений или требует ломать нынешний zoom/шторки, постоянный экземпляр не внедрять.

### 5. Проверить результат и выпускать по частям

Сначала отдельный небольшой diff этапа 2. Затем результат прототипа этапа 3. Нативный постоянный экземпляр — отдельное решение по результатам измерений; не объединять всё в один рефакторинг.

- Пройти имеющиеся проверки `src/lib/reader` и затронутых путей каталога; добавить только проверки новых ошибок/ветвлений.
- Для HTML выполнить `pnpm build:reader`; проверить согласованность исходника и сгенерированного asset.
- Повторить матрицу этапа 1. Запуск simulator — только штатным `script/build_and_run.sh`; нативная пересборка только отдельно при нативных изменениях.
- Проверить системный Back, zoom туда/обратно, оглавление, заметки, клавиатуру, TalkBack/VoiceOver, сворачивание/возврат, закрытие во время загрузки и принудительное завершение web content.
- Проверить, что фоновый прогрев не добавил фризы библиотеке. После серии из 20 открытий память должна стабилизироваться, а не расти на каждую книгу; измерять web content тоже. Числовой бюджет памяти назначить после baseline, а не угадывать.
- Рабочая цель для тёплых сценариев: убрать паузы более 200 мс из-за нашей работы на JS; это критерий приёмки, а не уже достигнутый результат. Полное время открытия должно улучшаться за пределами разброса повторов без ухудшения p95 и первого перелистывания.

## Скорость: что можно утверждать сейчас

Фактическое ускорение приложения ещё неизвестно: изменения не внедрены, полного A/B на телефоне нет. Проверен изолированный выигрыш повторного использования документа и воспроизведено ожидание медленных шрифтов.

Стенд использует текущий `reader.html`, настоящие локальные EPUB через HEAD/Range, четыре SB Serif, viewport 393 × 740, позицию 35%, настольные WebKit и Chromium. Сравниваются новый документ и заранее созданный документ с уже прогретыми шрифтами. На каждую книгу/режим/движок — 6 измерений; порядок режимов чередуется. В сумме 48 открытий за запуск. Кеш ответов выключен (`no-store`); это контролируемое условие, не точная копия кеша обеих мобильных платформ.

Время стенда: загрузка HTML до `ready` плюс `openBook` до `loaded`; для прогретого документа только вторая часть. Не входят создание нативной WebView, React, bridge-задержки, анимация, скачивание/импорт каталога, показ финального кадра, обработка персонажей из приложения. Это пилот с медианами, не статистика p95 и не доказательство корректности всех состояний постоянной WebView.

| Пользовательский сценарий | Ожидаемое изменение |
|---|---|
| Локальная книга, прогрев закончен | Убирается неперекрытая часть подготовки оболочки/общих шрифтов. На стенде это десятки миллисекунд; нативная часть пока не измерена |
| Нажатие сразу после запуска | Выигрыш от прогрева может быть нулевым: подготовка ещё не завершена |
| Новая книга из сети | Скачивание не ускоряется; подготовку оболочки можно перекрыть временем скачивания |
| Медленный/зависший шрифт | Вместо неограниченного ожидания — ограниченный бюджет ожидания шрифтов и стабильный fallback; весь ридер не обязан открыться за 750 мс |
| Вход по цитате | Убирается лишний начальный переход/раскладка; экономия равна стоимости этой работы в конкретной книге |
| Чтение уже открытой книги | Устраняются ежесекундные рендеры, вызванные только счётчиком времени; это улучшение плавности, не заявленные миллисекунды открытия |

Не суммировать проценты отдельных оптимизаций. Видимое время зависит от самого длинного незавершённого этапа, включая анимацию: подготовка, которая уже укладывалась внутри анимации, может вообще не влиять на момент появления страницы.

## Воспроизведение и границы проверки

Скрипт: `packages/app-expo/scripts/performance/reader-reuse-probe.mjs`. Из `packages/app-expo`:

```sh
node scripts/performance/reader-reuse-probe.mjs > /tmp/reader-reuse.json
```

Нужен доступный Playwright и его WebKit/Chromium; зависимости проекта не изменялись. В текущем окружении использовался уже установленный runtime:

```sh
NODE_PATH=/Users/manaer/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules node scripts/performance/reader-reuse-probe.mjs > /tmp/reader-reuse.json
```

Скрипт проверяет успешный `loaded` каждой книги, отсутствие reader/page errors, наличие текста и единственный `foliate-view`. Он не подтверждает нативное сохранение WebView или отсутствие утечек ресурсов. Полные результаты и SHA-256 HTML сохранены рядом в `reader-reuse-results-2026-09-24.json`.

В исходном ревью выполнены 29 тестовых файлов: 175 проверок прошли, 1 пропущена. Это проверка исходного состояния, не будущей реализации. Старые профили с паузами 459/543 мс не использованы как скорость открытия: там измерялись JS stalls, другая метрика.

Независимые проверки архитектуры и жизненного цикла выявили ограничения native preload, необходимость `book.destroy`, токенов и правильного порядка reset/начальных команд. Они включены в план как обязательные проверки, а не оставлены предположениями.

Источники API: [React Navigation: preload](https://reactnavigation.org/docs/navigation-object/#preload), [W3C: готовность шрифтов и раскладки](https://www.w3.org/TR/css-font-loading/#font-face-set-ready). Приоритет имеют установленный код зависимостей и проверка на устройстве.

Ближайший шаг реализации: исходный замер на устройстве и небольшой diff этапа 2. Для одного постоянного экземпляра сначала нужен нативный прототип; обещать ему конкретный процент ускорения сейчас оснований нет.
