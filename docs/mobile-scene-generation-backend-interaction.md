# Генерация сцен: взаимодействие мобильного клиента с backend

## Назначение документа

Документ фиксирует целевой контракт для встроенных в читалку сцен, разбор
инцидента 28 августа 2026 года и правила, которые не позволяют повторить
ошибки с тайм-аутами, сменой слота, signed URL и локальным сохранением файла.

Речь идёт о сцене для позиции читателя через
`POST /v2/books/:bookEditionId/scenes/at`. Ручная генерация по выделенному
пользователем тексту использует отдельный legacy-процесс
`/v2/media/scene/jobs`; эти два сценария нельзя смешивать.

## Продуктовые инварианты

1. Генерация backend-сцены начинается только после явного нажатия пользователя
   «Показать сцену».
2. Публикация разметки, запрос manifest, открытие книги и обновление прогресса
   чтения не должны автоматически добавлять сцены в очередь.
3. Scene-worker должен быть включён и постоянно готов принимать задания. Его
   выключение останавливает и явные пользовательские запросы; отсутствие
   автоматической генерации обеспечивается местами постановки в очередь, а не
   отключением worker.
4. Один слот сцены соответствует одной версии разметки и одному диапазону
   канонического текста. Повторные запросы этого слота идемпотентны и не должны
   создавать дублирующие задания или повторную стоимость.
5. Backend владеет каноническим текстом, scene policy, prompt, моделью,
   provider routing, durable job и публикацией asset. Мобильный клиент передаёт
   только идентификатор редакции книги и позицию чтения.
6. Клиент считает сцену готовой только после успешного скачивания и сохранения
   непустого файла. Статус `ready` на backend сам по себе ещё не означает, что
   картинка доступна пользователю офлайн.

## Предусловия

Для backend-пути у клиента должен быть `backendBinding.bookEditionId`. У книги
должны существовать опубликованная v3-разметка, нормализованный текст и
`scenePolicy`. Запрос проходит с installation-auth, которым управляет общий
`narraGatewayRequest`.

Если backend binding отсутствует, текущий клиент может использовать legacy
локальный путь генерации по видимому фрагменту. Нельзя незаметно переключаться
на legacy после ошибки backend для уже привязанной книги: это создаёт другую
сцену, другую стоимость и скрывает неисправность серверного контура.

## HTTP-контракт

### Запрос

```http
POST /v2/books/{bookEditionId}/scenes/at
Authorization: Bearer {installation-token}
Content-Type: application/json

{
  "progress_fraction": 0.385
}
```

Тело содержит ровно одно поле:

- `progress_fraction` — конечное число от `0` до `1`; мобильный клиент
  использует этот вариант;
- `reader_text_offset` — неотрицательное safe integer; допустим для клиентов,
  которые уже работают в координатах канонического текста.

Нельзя передавать excerpt, prompt, имена персонажей, provider, model или ключи
провайдера. Backend сам вычисляет слот по опубликованной политике, сейчас это
`text-interval-v1` с интервалом 6000 символов нормализованного текста.

### Ответ во время работы

Backend отвечает HTTP `202`:

```json
{
  "status": "queued",
  "scene_key": "text-interval-v1:6",
  "slot_index": 6,
  "anchor_text_offset": 39000,
  "poll_after_ms": 2000
}
```

`status` может быть `queued` или `running`. Клиент повторяет тот же запрос не
раньше `poll_after_ms`. Защитный default клиента — 2000 мс, нижняя граница —
250 мс.

### Готовый ответ

Backend отвечает HTTP `200`:

```json
{
  "status": "ready",
  "scene_key": "text-interval-v1:6",
  "slot_index": 6,
  "anchor_text_offset": 39000,
  "image_url": "https://object-storage.example/signed-url",
  "mime_type": "image/png",
  "expires_at": "2026-08-28T09:50:00.000Z"
}
```

`image_url` — короткоживущая signed URL, а не постоянный адрес asset. Клиент
должен скачать файл сразу. Если URL истекла или download завершился временной
ошибкой, клиент снова вызывает `/scenes/at` и получает новую signed URL.

`status: failed` — терминальный результат текущей попытки. Его нельзя маскировать
как timeout или автоматически заменять другой генерацией на клиенте. Повторное
пользовательское действие может запросить серверный retry по правилам durable
очереди.

## Правильный клиентский алгоритм

1. При нажатии сохранить `requestedProgress = progressRef.current`. Это snapshot
   позиции, а не ссылка на меняющееся состояние читалки.
2. Установить общий deadline ожидания результата: пять минут от начала действия.
   Это deadline polling-процесса, а не пяти-минутное открытое HTTP-соединение.
3. В каждом poll отправлять один и тот же `requestedProgress`. Перелистывание
   книги во время генерации не должно переключать запрос на другой scene slot.
4. При `queued` или `running` ждать `poll_after_ms` и повторять запрос.
5. Единичные сетевые, auth и download-сбои считать восстанавливаемыми до
   deadline. Installation-auth отдельно обновляет отклонённый token и повторяет
   запрос один раз.
6. При `ready` скачивать `image_url` через нативный `File.downloadFileAsync` во
   временный файл с `idempotent: true`.
7. Проверить, что временный файл существует и его размер больше нуля. Только
   затем удалить прежнюю локальную версию и переместить временный файл на
   стабильный путь. Такой порядок не оставляет store со ссылкой на пустой или
   частично скачанный файл.
8. Если ready-asset не скачался, не терять уже завершённую серверную работу:
   повторить `/scenes/at`, получить новую signed URL и снова скачать asset.
9. После истечения deadline выполнить один финальный recovery-запрос. iOS
   приостанавливает JavaScript timers в background, поэтому wall-clock deadline
   может пройти, пока приложение не выполняет polling.
10. Только после успешного локального сохранения записать сцену в Narra store,
    прочитать файл и передать data URI в WebView.
11. При окончательной ошибке перевести слот в retryable UI-state и записать
    техническую причину в telemetry. Пользовательское повторение должно
    обращаться к тому же идемпотентному backend-слоту.

Сейчас общий deadline равен `5 * 60 * 1000`, обычный сетевой timeout одного
короткого backend-запроса — 60 секунд, а период polling задаёт сервер. Эти три
величины решают разные задачи и не должны подменять друг друга.

## Что было сделано неправильно

### 1. Исправление свели только к увеличению тайм-аута

Первое изменение увеличило число попыток примерно до пяти минут. Это сняло
ранний обрыв ожидания, но не исправило получение и сохранение готового asset.
Нельзя объявлять такой инцидент исправленным, проверив только длительность
polling или только статус job в базе.

Правильно: проверять весь путь `tap -> job -> asset -> signed URL -> local file
-> store -> WebView`.

### 2. Polling читал меняющийся `progressRef.current`

Генерация занимает минуты, а пользователь может продолжить чтение. Если каждый
poll берёт новую позицию, backend законно вычисляет другой слот. Клиент ждёт уже
не ту сцену, которую поставил в очередь первым запросом, и может создать
несколько заданий.

Правильно: один раз зафиксировать позицию в момент нажатия и использовать её до
завершения этого действия.

### 3. Использовалось фиксированное количество poll-попыток

Сорок пять попыток при интервале около двух секунд давали примерно 90 секунд,
но реальная генерация диагностической сцены заняла около 131 секунды. Число
итераций также даёт разную фактическую длительность при другом
`poll_after_ms`.

Правильно: использовать wall-clock deadline и ограничивать каждую паузу
оставшимся временем.

### 4. Любая промежуточная ошибка немедленно завершала действие

Краткий сетевой сбой, обновление installation-token или ошибка скачивания
signed URL не отменяют durable job на backend. Немедленный выход превращал
восстанавливаемый сбой в пользовательскую ошибку.

Правильно: повторять короткие запросы до общего deadline, а терминальный
`status: failed` обрабатывать отдельно.

### 5. После background не выполнялась финальная проверка

iOS замораживает JavaScript timers. Когда приложение возвращается, deadline уже
может быть в прошлом, хотя backend давно завершил сцену.

Правильно: независимо от deadline выполнить один финальный запрос и попытку
скачивания готового результата.

### 6. Готовый asset скачивался legacy API без проверки результата

Backend job и объект в storage были `ready`, прямая signed URL возвращала полный
PNG, но в sandbox приложения файла не было. Простое получение `image_url` было
ошибочно принято за успешное завершение пользовательского сценария.

Правильно: использовать актуальный нативный Expo File API, скачивать во
временный файл, проверять `exists` и `size > 0`, затем атомарно публиковать
локальный файл.

### 7. Повторно использовалась бы старая signed URL

Signed URL ограничена по времени. Retry той же ссылки после задержки может
стабильно возвращать отказ, хотя asset исправен.

Правильно: при каждом download-retry заново получить `ready` через
`/scenes/at`; backend выдаст свежую ссылку.

### 8. Клиентский timeout путали с провалом backend job

Завершение ожидания на телефоне не отменяет durable job. Повторная генерация с
новым ключом привела бы к дублям и лишней стоимости.

Правильно: сохранять идемпотентность по редакции книги, версии разметки, версии
policy и индексу слота; после timeout сначала восстанавливать уже готовый asset.

### 9. Автопостановку сцен пытались останавливать выключением worker

Выключенный worker действительно не расходует генерацию, но одновременно
ломает endpoint для явного пользовательского запроса.

Правильно: worker включён, а автоматические enqueue-точки отсутствуют. Новый
`scene_image` job создаёт только `/scenes/at` после действия пользователя либо
явная ограниченная операторская кампания.

### 10. Manifest, прогресс или публикация разметки добавляли сцены в очередь

Такой warmup создаёт большой неуправляемый хвост, не связанный с намерением
пользователя, и делает стоимость генерации неожиданной.

Правильно: чтение manifest и обновление прогресса — read/update операции без
побочного enqueue сцен. Операторский backfill должен быть отдельной явной
командой с заранее рассчитанным объёмом.

### 11. Диагностика останавливалась на одной стороне системы

Статус «не сгенерировалось» не определяет место поломки. В зафиксированном
инциденте backend, worker и object storage были исправны, а сбой находился между
signed URL и локальным файлом мобильного клиента.

Правильно: коррелировать один запрос по `bookEditionId`, `sceneKey`, `jobId` и
`assetId`, а затем отдельно проверять серверную публикацию и клиентское
сохранение.

## Зафиксированный инцидент 28 августа 2026 года

Для книги «Деревня» (`bookEditionId`
`5f79199b-e75f-4e1f-94db-106c8250696f`) слот `text-interval-v1:0` был поставлен
в job `f511930e-180b-44f7-b2f0-f8ad0444347a`.

- job стартовал в `09:33:22Z` и завершился в `09:35:33Z`;
- фактическое время генерации — около 130,66 секунды;
- `generation_jobs.status` стал `ready`;
- опубликован asset `293900d1-2552-4dad-a6d0-ed4942ebf3d7`;
- PNG имел размер 3 360 581 байт;
- повторный `POST /scenes/at` вернул `ready`, а signed URL отдала тот же полный
  PNG;
- в sandbox мобильного приложения backend-файла не оказалось.

Эти данные доказали, что увеличение ожидания было необходимо, но не являлось
достаточным исправлением: реальной причиной последнего сбоя было отсутствие
надёжного recovery и persistence готового asset на мобильном клиенте.

## Диагностический чек-лист

1. Зафиксировать `bookEditionId`, отправленную позицию и время пользовательского
   действия.
2. Проверить первый `/scenes/at`: HTTP status, `status`, `scene_key`,
   `slot_index`, `poll_after_ms`.
3. Убедиться, что последующие poll-запросы используют ту же позицию и тот же
   `scene_key`.
4. Найти durable job и проверить `status`, `attempts`, lease, timestamps и
   `last_error_code`.
5. Проверить, что scene-worker запущен, принимает именно `scene_image` и не
   занят бесконечным retry другого задания.
6. При `ready` проверить связь `book_scene_slots.asset_id`, запись
   `media_assets`, MIME type и ненулевой `byte_size`.
7. Скачать свежую signed URL независимо от приложения и сверить HTTP status,
   MIME type и размер ответа. URL и auth-token не записывать в постоянные логи.
8. Проверить app log на стадии request, poll, download, move, store и WebView.
9. Проверить наличие и ненулевой размер файла в sandbox приложения.
10. После перезапуска приложения проверить восстановление сцены из стабильного
    локального пути без повторной генерации.

## Наблюдаемость

Для одного пользовательского действия полезно логировать безопасный correlation
record:

- `bookEditionId`, `sceneKey`, `slotIndex` и snapshot позиции;
- `jobId` и `assetId`, когда они доступны серверной диагностике;
- время enqueue, start, ready, первого успешного download и отображения;
- номер poll, HTTP status, класс retryable/terminal ошибки;
- MIME type и число скачанных байт;
- переход приложения background/foreground во время ожидания.

Нельзя логировать installation secret, bearer token, полную signed URL или
неограниченный текст книги.

## Минимальная матрица проверок

1. Уже готовая сцена возвращается первым запросом и сохраняется локально.
2. Новая сцена проходит `queued -> running -> ready` за 2–3 минуты без раннего
   timeout.
3. Пользователь перелистывает книгу во время ожидания, но клиент продолжает
   опрашивать исходный слот.
4. Первая signed URL истекает или download временно падает; клиент получает
   новую URL и сохраняет asset.
5. Приложение уходит в background дольше deadline; после возврата финальный
   recovery-запрос забирает готовую сцену.
6. Backend возвращает `failed`; UI показывает повторяемую ошибку и не запускает
   legacy fallback.
7. Installation-token истекает между poll-запросами и успешно обновляется.
8. Download возвращает пустой файл; сцена не записывается в store, выполняется
   retry.
9. После перезапуска готовая сцена восстанавливается из локального файла.
10. При включённом worker открытие catalog, manifest и обновление прогресса не
    создают `scene_image` jobs; нажатие «Показать сцену» создаёт ровно один job.

## Оставшийся технический долг

- Текст подсказки в UI «20–60 секунд» не соответствует наблюдаемым 2–3 минутам
  и пяти-минутному recovery deadline; его нужно заменить на честную
  формулировку без узкого обещания времени.
- Клиентской telemetry нужен единый correlation ID для всех poll и download
  попыток одного нажатия.
- Ошибки HTTP `400/404` следует отличать от временных `5xx/network`, чтобы не
  тратить весь deadline на заведомо невосстанавливаемый контрактный запрос.
- Нужен интеграционный мобильный тест с реальным локальным HTTP-файлом, а не
  только mock `File.downloadFileAsync`.
- Нужен серверный regression-тест, доказывающий отсутствие автоматических
  `scene_image` jobs после публикации разметки, чтения manifest и обновления
  прогресса при включённом scene-worker.
