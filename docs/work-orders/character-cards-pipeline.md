# Work Order: карточки персонажей по частотности имён и предгенерация первых глав

Статус: план, не реализовано. Исполнители: автономные агенты + ревью. Форма — work order
по методологии hill-climb. Дата плана: 2026-09-09.

## Mission

Заменить LLM-обход всей книги как способ *найти* персонажей на детерминированный частотный
проход и «скрапер» фрагментов, а LLM оставить только там, где он нужен: характер, биография,
местоположение, внешность по собранным фрагментам. Карточка персонажа создаётся один раз и
больше не меняется. Персонажи и сцены первых двух глав готовятся сразу после импорта; остальные
главы — в фоне. В сцену передаются портреты персонажей как изображения и последние 500 символов
текста перед точкой сцены.

## Требования (ТЗ ↔ решение)

| # | ТЗ | Решение | Что переиспользуем |
|---|---|---|---|
| 1 | Проходим по книге, вытаскиваем наиболее частотные имена | Детерминированный `name inventory` по всему normalized text в стадии Prepare: капитализованные токены/биграммы вне начала предложения, кластеризация русских падежных форм по основе, счётчики частоты, разброса по главам, соседства с прямой речью и обращениями. Один LLM-вызов на книгу подтверждает roster (человек/место/другое, склейка вариантов имени) | Prepare worker (полный текст уже на руках), `character-name-matcher.ts` (стемминг и окончания, переносим в gateway), лимит 128 персонажей, frozen identity fixtures для оценки |
| 2 | Скрапер подтягивает все фрагменты с упоминанием персонажа | Точные и падежные формы имени матчатся по границам слов; каждое совпадение даёт абзац-фрагмент с глобальными UTF-16 offsets. Общая фамилия двух персонажей одиночно не засчитывается. Фрагменты — это evidence: exact quote + offsets, как сейчас требует Validate | Правила матчера из reader (стоп-лист, MIN_STEM_LENGTH, однозначность), normalized text в MinIO, `content_navigation.segments` для chapter index |
| 3 | Из фрагментов выделяем характер, биографию, местоположение | Один LLM-вызов на персонажа: вход — фрагменты в пределах «окна карточки», выход — JSON с traits, bio, locations, appearance passport, gender, age; каждое утверждение ссылается на id фрагментов, сервер проверяет ссылки и границы окна | Generation service (`completeChat`, кэш по idempotency key, cost ledger), фильтры traits из `character-profile-v15` |
| 4 | Картинки по описанию; в карточке био и характер; био без спойлеров; карточка неизменяема | Портрет — существующий `character_portrait` job с passport из карточки. Спойлер-барьер структурный: в вызов попадают только фрагменты до конца окна карточки. Карточка — immutable строка с хэшами входа; изменения только через уже существующий correction overlay | `ensureCharacterMediaJobs`, `character-portrait-prompt.mjs`, bundle revision по source hash, `book_character_corrections` |
| 5 | Предгенерация «в моменте» только для первых двух глав; в сцену — портреты и последние 500 символов | Окно 1 = главы 1–2, ставится сразу после Prepare с высоким приоритетом. Сцены — слоты `text-interval-v1` внутри окна; scene job получает байты портретов упомянутых персонажей + excerpt из 500 символов до anchor. Провайдеру добавляется вход reference images | `bookSceneSlotAt` (уже даёт последние 500 символов), `ensureBookScenesThrough` (реализовано, вызовов нет), `generation_jobs.priority`, dependency gate как у `character_animation` |
| 6 | В фоне — картинки и персонажи следующих глав | Цепочка окон по главам: окно N+1 ставится после завершения окна N; для private книг ограничено frontier читателя (текущая глава + 2), для catalog — вся книга | `bookMediaFrontier`, `advanceProgress`, image gate и дневные бюджеты, operator pause |

## Ключевые архитектурные решения

### D1. Roster определяется по всей книге, карточка — по своему окну

Частотность считается по всему тексту сразу (это дёшево и детерминированно), поэтому список
персонажей известен после Prepare. Но карточка персонажа строится не из всей книги, а из
фрагментов в пределах **окна карточки**: от начала книги до конца главы, следующей за главой
первого упоминания. Для персонажей первых двух глав окно совпадает с главами 1–2. Карточка
создаётся, когда окно обработано, и после этого не меняется.

Почему так: unlock карточки в reader остаётся по `firstAppearanceTextOffset`. Если бы био
строилось из всего обработанного текста, читатель на главе 1 увидел бы факты из главы 8. Окно
«глава появления + 1» даёт биографию из основных фактов без забегания вперёд и одновременно
делает результат воспроизводимым: одинаковое окно — одинаковый вход — одинаковый хэш.

### D2. Инкрементальная публикация карточек вместо barrier-публикации всей книги

Текущий `book-markup-v3` публикуется атомарно после обработки всей книги. Карточки же должны
появляться по главам. Вводится отдельная immutable сущность `book_character_cards`
(одна строка на `characterKey`, контракт `character-card-v1`), которую manifest отдаёт
клиенту по мере готовности. `book-markup-v3` не меняется и не ломается: после обработки
последнего окна из карточек детерминированно собирается v3-проекция (union карточек +
evidence), чтобы TTS sidecar, chat и graph продолжали работать на прежнем контракте.

### D3. LLM только на двух узких задачах

| Задача | Вызовов на книгу | Вход |
|---|---|---|
| Подтверждение roster | 1 (до 2 при >128 кандидатов) | до 128 кандидатов, по 2 коротких фрагмента на каждого |
| Карточка персонажа | K (число персонажей) | фрагменты окна, до 48 KB |

Для «Гордости и предубеждения» это порядка 40–50 вызовов вместо 182 scan + 3×K synthesize.
Сканирующий LLM-проход по каждому чанку не выполняется.

### D4. Сцена получает изображения, не текст внешности

Текущие провайдеры (`gpt-image-2`, `gemini-3.1-flash-image` через OpenRouter/LiteLLM,
Kandinsky) вызываются только промптом. Нужен новый вход `referenceImages[]` в абстракции
провайдера. gpt-image-2 и gemini flash image принимают входные изображения; Kandinsky — нет
и остаётся текстовым fallback. Промпт сцены: excerpt из 500 символов + имена упомянутых
персонажей + указание «внешность персонажей — строго по приложенным портретам»; текстовый
appearance passport не передаётся, если есть портрет.

## Контракт `character-card-v1`

```json
{
  "contractVersion": "character-card-v1",
  "characterKey": "char:elizabeth-bennet",
  "name": "Элизабет",
  "fullName": "Элизабет Беннет",
  "aliases": ["Лиззи", "мисс Беннет"],
  "firstMentionTextOffset": 8132,
  "cardWindow": { "startOffset": 0, "endOffset": 61240, "chapterIndexes": [0, 1] },
  "mentionCount": 2476,
  "mentionCountInWindow": 214,
  "traits": [{ "value": "наблюдательная", "fragmentIds": ["frag:..."], "confidence": 0.9 }],
  "bio": { "value": "Вторая из пяти дочерей семьи Беннет...", "fragmentIds": ["frag:..."] },
  "locations": [{ "value": "Лонгборн", "fragmentIds": ["frag:..."] }],
  "appearancePrompt": "...",
  "gender": "female",
  "age": "около двадцати",
  "source": {
    "normalizedTextHash": "sha256:...",
    "inventoryVersion": "name-inventory-v1",
    "fragmentSetHash": "sha256:...",
    "promptVersion": "character-card-prompt-v1"
  },
  "createdAt": "2026-09-09T10:00:00Z"
}
```

Инварианты:

1. Каждый `fragmentId` существует, принадлежит этому персонажу и лежит внутри `cardWindow`.
2. Строка карточки не обновляется. Новая карточка того же `characterKey` возможна только как
   новая `cardRevision` по явной операторской команде; reader всегда читает последнюю
   включённую revision.
3. Точечные правки текста — через существующий correction overlay, а не мутацией карточки.

## Хранение

| Таблица | Назначение |
|---|---|
| `book_name_inventory` | одна строка на run: JSONB с кластерами имён, счётчиками, `inventoryVersion`, хэш текста |
| `book_character_fragments` | `(run_id, character_key, fragment_id, start_offset, end_offset, chapter_index)`; текст не дублируется — читается byte-range из normalized text |
| `book_card_windows` | окна по главам: `(run_id, window_index, start_offset, end_offset, status, priority_class)` |
| `book_character_cards` | immutable карточки `character-card-v1`, `card_revision`, `enabled` |
| `generation_jobs` | новые `job_type`: `name_inventory`, `roster_confirm`, `character_card`; сцены и портреты — существующие типы |

MinIO: normalized text и результаты генераций — без изменений; портреты и сцены — прежние
ключи `generated/{scope}/{edition}/characters/...` и `.../scenes/...`.

## Планирование и приоритеты

| Работа | Приоритет | Условие постановки |
|---|---|---|
| `name_inventory` | 65 | сразу после Prepare |
| `roster_confirm` | 65 | после inventory |
| `character_card`, окно 1 (главы 1–2) | 65 | после roster |
| `character_portrait`, персонажи окна 1 | 65 | после карточки; гейт `character_card ready` |
| `scene_image`, слоты окна 1 | 60 | после портретов упомянутых персонажей или по таймауту 10 минут с текстовым fallback |
| окна 2..M: карточки, портреты, сцены | 45 | окно N+1 после завершения окна N; private — не дальше frontier «глава читателя + 2» |
| tap читателя по слоту сцены | 70 | без изменений |

Определение «главы»: `content_navigation.segments` из Prepare (character offsets). Если
navigation отсутствует (TXT без заголовков) — окна по 30 000 символов с границей на абзаце.
Первые две главы короче 8 000 символов суммарно расширяются до ближайшей границы главы, чтобы
окно 1 содержало хотя бы один слот сцены.

## Фазы

### P0. Контракт и решения (1–2 дня)

- Зафиксировать `character-card-v1`, миграцию таблиц, правило окна карточки (D1), стратегию
  публикации (D2) в `book-analysis-contracts.mjs` и `docs/architecture/components/book-enrichment.md`.
- Решить с продуктом: окно карточки «глава появления + 1» или «главы 1–2 фиксированно, далее по
  одной главе». План исходит из первого.
- Acceptance: контракт и миграция проходят ревью; ни один существующий тест не меняется.

### P1. Name inventory + скрапер (детерминированно, 0 LLM)

- Новый модуль `book-name-inventory.mjs`: токенизация, стемминг (порт `stemNameToken`,
  `NAME_ENDINGS`, `NAME_STOPWORDS` из `character-name-matcher.ts` в общий пакет или копия с
  тестом на идентичность), английские honorific-биграммы, статистики: count, chapter dispersion,
  доля позиций в начале предложения, доля соседства с речевыми глаголами и тире-диалогом, доля
  предложных контекстов (в/на/из, in/at/to) как сигнал места.
- Порог roster: минимальный убывающий по частоте префикс, покрывающий 95 % упоминаний имён
  (тот же протокол, что `significant` в gold fixtures), не более 128; остальные — `minor`.
- Скрапер `book-character-fragments.mjs`: все совпадения форм имени → абзацы с offsets; дедуп по
  абзацу; лимит на персонажа для LLM-входа — до 240 фрагментов, равномерно по окну.
- Оценка: `evaluation/score-frozen-identity.mjs` на 8 fixtures — significant recall ≥ 0.90,
  precision ≥ 0.80 до LLM-подтверждения. Юниты: Раскольников/Раскольникова/Раскольникову — один
  кластер; два Малфоя — одиночная фамилия не засчитывается; «Сегодня», «Бог», названия глав —
  не персонажи.

### P2. Подтверждение roster (1 LLM-вызов)

- `roster_confirm`: до 128 кандидатов с двумя фрагментами → `{person|place|group|other}`, склейка
  вариантов имени (никнеймы, обращения) с указанием basis; сервер принимает merge только между
  кандидатами inventory и отвергает merge при коллизии пола/родства (перенос hard-guards из
  `book-analysis-identity-reconciliation.mjs`: `forbiddenPairs`, gender collision).
- Лексикон уменьшительных RU/EN (Саша/Александр, Kitty/Catherine) как детерминированный
  генератор пар, не автослияние.
- Acceptance: на 8 fixtures significant P/R/F1 ≥ 0.90, critical merges 0; roster детерминирован
  при повторе на том же тексте (кэш по idempotency key).

### P3. Карточка персонажа и её публикация

- `character_card` job: вход — фрагменты окна, метаданные книги, roster; промпт
  `character-card-prompt-v1`: 3–6 traits, bio до 3 предложений только из фактов фрагментов, без
  исходов событий, locations, appearance passport, gender, age; каждое поле — `fragmentIds`.
- Валидация: ссылки существуют и внутри окна; traits проходят фильтры `character-profile-v15`
  (запрещённые категории, синонимы, конфликты); пустое bio → extractive fallback из первых
  фрагментов, как в `character-profile-v8`.
- Запись immutable строки; manifest v3 отдаёт карточки как `characters[]` c тем же набором
  полей, что сегодня (`role`, `description` ← bio, `traits`, `appearancePrompt`, `greeting`),
  плюс `cardStatus: ready|pending` для персонажей roster без карточки.
- Клиент: `ReaderCharacterCard` показывает «Био» и «Характер» из карточки без изменений
  разметки; для `pending` — существующий teaser. Unlock по `firstMentionTextOffset`.
- Acceptance: blind-аудит 10 карточек на двух книгах — ни одного факта из текста за окном;
  cited-evidence precision ≥ 0.90 (методика из `book-markup-stabilization-log.md`).

### P4. Портреты из карточки

- `ensureCharacterMediaJobs` получает `appearancePrompt` из карточки; `source_markup_hash` →
  хэш карточки, поэтому revision меняется только с новой `card_revision`.
- Приоритет 65 для окна 1, 45 для фоновых окон; audio/animation — прежние гейты.
- Acceptance: после импорта катaложной книги портреты персонажей глав 1–2 готовы раньше любого
  портрета глав 3+ (проверка по `generation_jobs.created_at/finished_at`).

### P5. Сцены с портретами

- `providers.mjs`: вход `referenceImages: [{bytes, mimeType, label}]` для OpenRouter/LiteLLM
  image-моделей; Kandinsky игнорирует и получает текстовый fallback.
- `scene-generation.mjs`: если у упомянутого персонажа есть ready portrait — прикладываем байты и
  убираем текстовый passport; иначе текущий текстовый путь. Упомянутые персонажи определяются
  тем же матчером по excerpt из 500 символов, а не только по `first_appearance <= excerpt_end`.
- Оживить `ensureBookScenesThrough` для слотов окна; dependency gate: сцена ждёт портреты
  упомянутых персонажей окна, но не дольше 10 минут.
- Acceptance: юнит на сборку запроса с 1–3 портретами и без; e2e на одной книге: сцены глав 1–2
  созданы без tap; при недоступности image-input — fallback без ошибки job.

### P6. Планировщик окон и бюджеты

- Цепочка окон: завершение окна N ставит окно N+1; private — гейт `bookMediaFrontier` с новым
  режимом «глава читателя + 2» (замена плоских 10 %); catalog — вся книга.
- Бюджеты: сцены предгенерации проходят `reserveSceneJobBudget` с отдельным лимитом на книгу
  (например, 12 сцен для окна 1, далее 4 на главу); operator pause распространяется на новые
  job types; `generation_cost_events` получает `stage=card|inventory|roster`.
- Acceptance: нагрузочный прогон 5 книг: окно 1 каждой книги завершается до старта окна 3 любой
  другой (проверка приоритетов); превышение бюджета не роняет run, а откладывает сцены.

### P7. Совместимость и rollout

- После последнего окна: детерминированная сборка `book-markup-v3` из карточек и фрагментов,
  проход существующего Validate, publish — чтобы TTS sidecar, chat и graph работали без изменений.
- `pipeline=cards` в `book_analysis_runs` рядом с `narra|external`; включение по флагу на
  catalog-книгах-канарейках; сравнение с текущим v52 по frozen fixtures и по стоимости.
- Acceptance: canary из `scripts/qa/book-analysis-pipeline-canary.mjs` зелёный; отчёт
  стоимости на 3 книгах; решение о дефолте.

## Риски и открытые вопросы

1. **Повествование от первого лица.** Частотный проход не найдёт безымянного рассказчика.
   Вариант: pseudo-персонаж `narrator` при доле «я» вне диалогов выше порога (детектор уже есть в
   `voice-rules.ts`). Требует решения продукта.
2. **Книги без глав.** TXT и часть FB2 не дают navigation; окна по 30 000 символов — грубая
   замена, спойлер-барьер тогда не совпадает с главой.
3. **Image-input у провайдеров.** Точная форма запроса зависит от роутера (OpenRouter chat с
   image parts против `/images/edits`); нужен spike на 1 день до P5.
4. **Два источника roster** до полной обработки книги: карточки и (если был) старый v3. Для
   книг на `pipeline=cards` v3 не публикуется до последнего окна; manifest читает карточки.
5. **Стоимость сцен предгенерации для private книг.** Даже 4 сцены на главу при активном
   чтении — заметный бюджет; лимиты в P6 обязательны, отключение по флагу.
6. **Русский gold.** Идентичность измерена только на английских fixtures; «Пиковая дама» и
   «Преступление и наказание» с двойной разметкой остаются обязательными до включения по
   умолчанию (см. `book-markup-stabilization-log.md`).

## Что не входит

- Изменение чата персонажей, TTS sidecar, search/graph.
- Прогрессивные personality snapshots: карточка одна, характер фиксирован окном.
- Ручной редактор карточек в приложении: правки только через correction overlay.
