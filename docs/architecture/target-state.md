# Narra: повторный импорт личной книги — спецификация и инструкция агентам

Документ предназначен для передачи другому агенту как самостоятельное задание на реализацию. Здесь описано **целевое поведение**, а не уже выполненные изменения. Реализацию, сборку приложения и E2E ещё предстоит выполнить.

## 1. Задание и границы

Реализовать управляемый повторный импорт одного и того же файла личной книги. При явном импорте мобильное приложение обращается к бэкенду, который возвращает существующую редакцию либо создаёт новый `bookEditionId` в зависимости от временной отсечки. Новая редакция должна заново пройти действующий пайплайн: обработка исходника, разметка, персонажи, предусмотренная пайплайном генерация портретов и работа со сценами.

Обязательные требования пользователя:

1. Репозиторий — `https://github.com/mishanaer/Narra.git`, базовая ветка — актуальная `origin/main`.
2. Реализация в отдельном Git worktree и отдельной ветке `codex/...`. Чужие рабочие каталоги и изменения не трогать.
3. Эту спецификацию обязательно включить в коммиты ветки реализации.
4. Мобильные изменения скрыть за **локальным фиче-тоглом внутри мобильного приложения**. Это не серверный и не удалённо управляемый флаг.
5. **UI мобильного приложения не должен измениться вообще:** никаких новых кнопок, переключателей, диалогов, экранов, надписей или индикаторов. В том числе не добавлять UI для тогла.
6. Серверный выключатель — `PRIVATE_BOOK_REIMPORT_REUSE_WINDOW_SECONDS`. Если переменная отсутствует либо равна `0`, сохраняется прежнее правило выбора/создания редакции. Положительное значение включает отсечку в секундах для нового явно обозначенного импорта.
7. Точное совпадение с доступной каталожной книгой возвращает каталог. Личную редакцию в этом случае не создавать; каталожную книгу, её разметку и исходник не заменять.
8. Использовать `Idempotency-Key`, чтобы повтор одного запроса не создавал следующую редакцию.
9. Устранить пересечение путей исходников разных редакций.
10. **Не дорабатывать заполнение `source_uploaded` в `/local` и `/resolve`.** Пользователь осознанно исключил эту оптимизацию. Повторная передача EPUB допустима; повторная генерация из-за неё — нет.
11. До тестового прогона провести ревью реального diff с использованием скилла `agentic-pr-review`.
12. Проверять E2E в реально собранном и запущенном iOS-приложении. Бэкенд, PostgreSQL и объектное хранилище поднять **локально в Docker**. Пользователь разрешил запуск Docker.
13. Файлы книг уже находятся в iOS Simulator. Сценарии записывать на видео отдельно. На время длительного ожидания запись останавливать, после ожидания запускать новый клип того же сценария.
14. Не переусложнять решение: использовать текущие API, репозитории, транзакции, очередь удаления, пайплайн и сборочные скрипты. Не добавлять отдельный сервис импорта, брокер, общий фреймворк идемпотентности, новую систему флагов или счётчики ссылок на общие исходники.

Продакшен не разворачивать и не изменять. Не запускать тесты против production-БД, bucket или gateway. Не менять модели, провайдеры, retry/fallback-политику генерации и таймауты ради прохождения этих тестов. Не обновлять зависимости, Expo, Pods или Xcode без конкретной необходимости для задания. Создание PR, push, merge и деплой этим документом автоматически не разрешаются: результат — проверенная ветка с коммитами и доказательствами.

## 3. Агенты, роли и модели

Пользователь разрешает распределить работу по ролям. Не запускать три независимые реализации и не заставлять каждого агента заново исследовать весь репозиторий.

| Роль | Рекомендуемая модель / reasoning | Ответственность и момент подключения |
| --- | --- | --- |
| Разработчик, ведущий работу | `gpt-6.1-sol`, `high` | Реализация backend и mobile, миграция, автоматические проверки, исправления. Единственный владелец продуктового кода и коммитов. |
| Архитектор и независимый reviewer | `gpt-6-astra`, `high` | Короткая проверка спецификации/инвариантов до разработки; затем ревью diff перед тестированием через `agentic-pr-review`. Проверяет транзакции, гонки, выключатели, совместимость и отсутствие лишней архитектуры. Не пишет параллельную реализацию. |
| QA | `gpt-6.1-sol`, `medium`; `high` только для сложного разбора гонки/сбоя | Готовит сценарии, собирает/запускает iOS, владеет Simulator и локальным Docker во время прогона, записывает видео и evidence. Не объявляет успех на основании ответа API без проверки приложения и БД. |

Это инженерная рекомендация, не утверждение о фиксированной стоимости. Официальное руководство [Model selection](https://developers.openai.com/api/docs/guides/model-selection) предлагает Sol для сложной технической работы с учётом стоимости, Astra — для более требовательного анализа, а настройки выбирать по результату. Доступность точных моделей проверить в используемом клиенте. Не использовать `max/ultra` по умолчанию.

Экономия токенов:

- Архитектор работает в двух коротких проходах и при необходимости разбирает конкретное противоречие; он не следит за каждым действием разработчика.
- QA заранее получает таблицу тестов, базовый/итоговый SHA, контракт и точки наблюдения. Ему не нужен весь эмоциональный контекст разговора.
- Ожидание LLM — ожидание событий/логов с разумным интервалом, а не постоянные запросы агентам.
- Архитектор/reviewer получает спецификацию и diff, а не неподтверждённое «разработчик всё проверил».
- Только один агент управляет Simulator/Metro/Docker в момент E2E. Во время проверки зафиксировать SHA; не менять под QA рабочий код.
- QA может добавлять тесты/артефакты в согласованной области; продуктовые исправления передаёт разработчику.

Проверенные особенности:

- `bookEditionId` — UUID бэкенда; он не вычисляется из SHA-256.
- В БД уникальна пара `(owner_subject_id, content_sha256)` для `scope='private'`. Не удалять этот индекс ради хранения нескольких активных редакций.
- `/local` уже ищет каталог, затем личную редакцию; при настоящем истечении `expires_at` ставит файлы в очередь и удаляет старую запись.
- `expires_at` — скользящий TTL. `updated_at` и TTL меняются при обращениях; использовать их для новой отсечки нельзя.
- `/resolve` находит действующую редакцию и может продлевать retention. Его нынешнюю семантику не менять и не добавлять в него замену редакции.
- Клиент обычно вычисляет MD5 для локального дубликата, а SHA-256 использует для backend identity. Не делать отдельную миграцию локальных хэшей.
- Найденный локальный дубликат сейчас сохраняет локальную книгу и серверную привязку. Именно обход server registration из-за сохранённой привязки надо изменить для явного импорта при включённом мобильном флаге.
- Старый путь исходника: `books/private/{userId}/{contentHash}/source`. При замене редакции старая очередь удаления может удалить файл новой по тому же пути.
- `source_uploaded` сейчас не заполняется в `bookBinding()` для `/local` и `/resolve`; parser клиента считает отсутствующий признак `false`. Пользователь разрешил оставить повторную передачу EPUB.
- Прежние серверные E2E с названием `book-backend.e2e.test.mjs` содержат derived-markup/fake generator. Они полезны для регрессий, но **не доказывают** прохождение реального современного пайплайна из iOS.

## 5. Два независимых выключателя

### 5.1. Локальный флаг мобильного приложения

Использовать существующий локальный механизм, если он подходит. Иначе один простой build-time флаг:

```ini
EXPO_PUBLIC_PRIVATE_BOOK_REIMPORT_ENABLED=false
```

Читать статическим `process.env.EXPO_PUBLIC_PRIVATE_BOOK_REIMPORT_ENABLED === 'true'`, совместимым с Expo bundling. По умолчанию `false`. Не заводить remote config, запрос настройки на сервер, UI переключатель или отдельный feature management SDK.

При `false`: весь прежний поток импорта/дубликатов/binding остаётся прежним; не создавать новые import operations и не добавлять запросы `/local` ради новой функции. При `true`: только явное действие импорта проходит новый путь. Открытие reader, background refresh, 404 recovery и восстановление обычного binding сами по себе не получают `intent`.

Флаг принадлежит приложению. Серверная env не включает его на телефоне. Изменение build-time env требует загрузки нового JS bundle/перезапуска соответствующего Metro; простой reload старого bundle не считать доказательством переключения. Для приёмки нужна реальная iOS-сборка; один JS unit-test её не заменяет.

### 5.2. Серверный выключатель и время

```ini
# Повторное создание личной редакции при явном импорте.
# Секунды; отсутствует/пусто/0 = прежнее правило переиспользования редакции.
# >0 = разрешить замену после указанного интервала.
# Это не TTL хранения: PRIVATE_MATERIAL_TTL_DAYS продолжает действовать отдельно.
PRIVATE_BOOK_REIMPORT_REUSE_WINDOW_SECONDS=0
```

Дефолт строго `0`. Положительный production-порог пользователь ещё не назначил; не придумывать и не включать его в production. Для локального QA выбрать удобное значение, например `120` секунд, и записать его в отчёте.

Парсить как безопасное неотрицательное целое число секунд. Для отрицательного, дробного, нечислового значения и переполнения не включать функцию молча; использовать явную ошибку конфигурации при старте. Проверить env на процессе gateway внутри контейнера, не ограничиваться host `.env`.

Описание добавить в поддерживаемый репозиторием env example и deployment-документацию. В проверенном checkout есть `services/narra-gateway/.env.example` и `book-analysis-local.env.example`, но tracked `app.env` не найден. Реальный `app.env` — конфигурация окружения: если так называется локальный env-файл стенда, добавить туда тот же комментарий и тестовое значение; секретный файл не коммитить. Не создавать второй произвольный production-шаблон вместо установления текущей конфигурационной цепочки.

### 5.3. Матрица поведения

| Mobile flag | Server window | Запрос при явном импорте | Выбор редакции |
| --- | --- | --- | --- |
| off | отсутствует / 0 | Прежний путь | Прежний |
| off | >0 | Прежний путь, без `intent` | Прежний; новые правила не применяются |
| on | отсутствует / 0 | `/local` с `intent` и ключом | Прежний каталог/TTL/reuse; возраст сам по себе ничего не удаляет |
| on | >0 | `/local` с `intent` и ключом | Новая временная отсечка |

Уточнение границ выключения: серверный `0` выключает **замену по возрасту**, а не поддержку добавленного контракта. Уже принятые idempotency keys продолжают защищать повторы, новый `explicit_import` при `0` можно сохранить с результатом старого правила. Это не запускает регенерацию. Формат безопасного пути новых файлов также не возвращать к общему пути при выключении: переключение env не должно вновь создавать коллизии с отложенной очисткой. Пользовательский результат при `0` соответствует прежней схеме.

## 6. Контракт `/local`

Сохранить endpoint `POST /v2/books/local`, авторизацию installation/subject и существующие поля/статусы ответа. Добавить только необязательный `intent`:

```http
POST /v2/books/local
Authorization: Bearer <installation token>
Idempotency-Key: <UUID одного действия импорта>
Content-Type: application/json
```

```json
{
  "content_sha256": "64 lowercase hex characters",
  "title": "Название",
  "author": "Автор",
  "format": "epub",
  "language": "ru",
  "intent": "explicit_import"
}
```

`language` остаётся необязательным по текущему контракту. UUID в ключе генерируется **клиентом один раз на действие**, а `bookEditionId` — сервером. Не путать их.

- Без `intent`: legacy path; не требовать ключ и не применять отсечку даже при положительной env.
- `explicit_import`: требовать валидный ключ, ограничить размер header, использовать current validation/error conventions.
- Неизвестный `intent`/невалидный ключ: предсказуемый `400`, никаких изменений данных.
- Один ключ с несовпадающим нормализованным payload/fingerprint: `409` с стабильным кодом, например `IMPORT_IDEMPOTENCY_CONFLICT`.
- Проверить, что HTTP-wrapper и повтор после refresh installation token сохраняют header и body. Bearer/token/timestamp запроса не включать в fingerprint. Если в gateway явно ограничены CORS headers, добавить новый header адресно, без ослабления авторизации.
- Старый ключ с уже удалённой, недоступной или просроченной target edition: `410` с кодом `IMPORT_OPERATION_EXPIRED`. Не создавать новую под этим ключом и не преобразовывать ошибку в скрытый новый import.
- Same key принадлежит тому же authenticated subject. Не разрешать переданный в body `userId`; владельца брать из существующей авторизации.
- Существующий ответ `resolution: catalog/private`, `book_edition_id`, metadata сохранить. Новые типы `private_created`/`private_reused` не нужны: клиент сравнивает ID и resolution.
- Не обещать побайтово идентичный JSON через неделю: сохраняется решение операции и её целевая редакция; текущие метаданные можно читать заново. Удалённый ID не выдавать как работоспособный.
- Не добавлять заполнение `source_uploaded` для `/local`/`/resolve`, новые HEAD/status endpoints и оптимизацию передачи EPUB.

## 7. Правило выбора и временная граница

Для **нового** ключа `explicit_import`:

1. Найти доступную каталожную книгу по точному SHA-256 с теми же допустимыми статусами, что в нынешнем `/local`. При совпадении вернуть её ID, запомнить решение, завершить обработку. Не удалять существующую private edition только потому, что теперь найден каталог.
2. Найти личную редакцию по authenticated subject + SHA-256.
3. Если редакции нет — создать.
4. Если `expires_at <= database_now` — применить существующее правило истечения TTL: заменить независимо от нового window, даже когда window=0.
5. Если intent отсутствует или window=0 — применить legacy reuse.
6. Иначе получить начало текущей canonical analysis: `started_at` актуального canonical run, если есть; если разметка ещё не стартовала — `book_editions.created_at`. Не выбирать произвольный shadow/экспериментальный run и не использовать `updated_at`, срок хранения или время открытия книги.
7. `database_now < anchor + window` — вернуть существующий ID. При точном равенстве и после границы (`>=`) — заменить редакцию.

Время и сравнение должны быть согласованы с PostgreSQL, а не зависеть от часов телефона. Вычислять decision time после ожидания сериализующей блокировки; `now()` в PostgreSQL фиксируется на начало транзакции, поэтому длительное ожидание нельзя незаметно превратить в неверную проверку границы. Использовать один явно выбранный момент принятия решения.

Сам факт `queued/running` не превращать в скрытую вечную защиту от замены: согласованное правило — новый явный импорт после отсечки заменяет редакцию, даже если предыдущая генерация затянулась. Внутри окна и при повторе **того же ключа** работа продолжается. Обычные `/resolve`, manifest/progress/identity запросы не разрешают замену по возрасту.

## 8. Идемпотентность: небольшая постоянная таблица

Добавить минимальную таблицу `book_import_requests` новой миграцией в текущем механизме. Не править уже применённые миграции и не фиксировать номер новой миграции до проверки свежего `main`.

Достаточные поля:

| Поле | Назначение |
| --- | --- |
| `owner_subject_id UUID` | Authenticated владелец |
| `request_id UUID` | Idempotency-Key |
| `request_fingerprint` | Стабильный SHA-256 нормализованных существенных входных полей |
| `book_edition_id UUID` | Редакция, выбранная этой операцией |
| `resolution` | `private` либо `catalog` |
| `created_at TIMESTAMPTZ` | Когда результат операции сохранён |

Primary key — `(owner_subject_id, request_id)`. Не хранить EPUB, токены, provider keys и лишние метаданные. Нормализация запроса фиксирована; мобильный retry отправляет сохранённый payload, а не изменённые позже title/author.

Запись операции **не должна исчезать каскадно при удалении target edition**. Простейшее решение — сохранить UUID без FK с `ON DELETE CASCADE`, проверять доступность target edition при replay. Не удалять ключи вместе с семидневным TTL книги: иначе поздний повтор будет ошибочно считаться новым импортом. В этой задаче не вводить отдельный планировщик очистки ключей. Это небольшие технические метаданные; политика их будущего удаления должна учитывать невозможность повторного исполнения истёкшей операции и удаление аккаунта.

Сохранение результата и изменение edition — одна транзакция. Отдельного распределённого idempotency-сервиса/Redis не нужно. Таблицу `book_analysis_retry_requests` не переиспользовать: у неё другая семантика и каскадное удаление.

Проверка повторного ключа предшествует новому выбору по каталогу/window. Иначе один и тот же запрос может сначала вернуть private, а после появления каталога — другой ID. При server window=0 уже сохранённые ключи также должны обрабатываться безопасно.

## 9. Транзакция, блокировки и побочные эффекты

Сохранить одну действующую личную edition на `(owner, hash)`. Не вводить параллельные поколения в одном edition и не менять общий pipeline.

Для явного импорта сериализовать по `(owner, request_id)` и по `(owner, content_sha256)` в фиксированном порядке; для legacy `/local` — по тому же `(owner, hash)`. Использовать существующий подход PostgreSQL transaction-scoped advisory lock либо равноценную минимальную схему. Одного `SELECT ... FOR UPDATE` недостаточно, когда строки ещё нет; один unique index также не решает безопасную замену одновременно с replay.

Псевдокод (структуру адаптировать к текущему repository, а не создавать второй сервис):

```text
validate/authenticate
BEGIN
  если explicit_import:
    lock(owner, request_id)
    проверить сохранённый результат
    при replay вернуть его или typed expired/conflict error

  lock(owner, content_sha256)
  взять согласованные row locks, прочитать текущие данные заново
  вычислить decision_time
  проверить каталог и правило reuse/replace

  если replace:
    собрать object_key старой редакции в существующую очередь удаления
    удалить старую edition и зависимые данные штатным способом
    INSERT новой edition с новым серверным UUID

  если explicit_import:
    INSERT результата операции
COMMIT
return binding
```

Транзакция не содержит вызовов S3/LLM, загрузки EPUB или ожидания провайдера. При исключении до COMMIT откатываются старая разметка, создание новой записи, новая запись операции и новые заявки очистки. Другие независимые ранее зафиксированные TTL-cleanup операции эта транзакция не отменяет; проверять целевую живую edition и не обещать глобальный откат всего стенда.

Физическое удаление старых объектов — только existing cleanup worker после COMMIT. Он не видит незафиксированную заявку. При ошибке S3 заявка остаётся для retry. Не выполнять S3 delete напрямую из `/local`.

Проверить совместную работу с TTL cleanup, source upload, analysis retry, progress и manifest: согласованный порядок блокировок, ограниченные транзакции, отсутствие deadlock. Ошибки сериализации/deadlock, если текущий стек их повторяет, повторяются с исходным ключом. Не держать DB lock во время отправки ответа или provider request.

Удаление старой edition аннулирует её задания/ссылки. Уже отправленный LLM-запрос может физически завершиться позже; его результат не должен опубликоваться в новой редакции. Не обещать мгновенное прерывание внешнего провайдера. Проверять identity/lease/version при фиксации старого результата, не допускать восстановления удалённой edition через UPSERT.

## 10. Безопасность исходников и повторный PUT

Для впервые создаваемой записи исходника использовать:

```text
books/private/{ownerSubjectId}/{bookEditionId}/source
```

Достаточно этого пути; `contentHash` можно хранить в существующих полях БД, дополнительная иерархия и refcount не нужны.

Для edition с существующим `book_files.object_key` читать и повторно использовать этот сохранённый адрес. Не пересчитывать адрес уже загруженного legacy-файла только потому, что код обновился. Никакого массового переноса/удаления прежних файлов.

Проверить на свежем коде, что normalized text, портреты, сцены и provider-result cache различаются по edition/run/job identity. В проверенном коде normalized text использует run ID, generated media — edition ID. Не менять их без обнаруженной коллизии.

Повторный `PUT /v2/books/{id}/source`:

- Проверяет owner, действительность edition, SHA-256, MIME и размер по текущим правилам.
- Для уже `ready` совпадающего исходника повторную запись в S3 не выполняет.
- Не переводит готовую книгу обратно в новую независимую генерацию; существующий `ensureCanonicalAnalysis` должен переиспользовать run/jobs при неизменных edition/input/pipeline identity.
- При частичной/неуспешной загрузке повторяет загрузку целиком в тот же ID; resume-bytes в задачу не входит.
- Одинаковые одновременные PUT могут потребовать штатной защиты от повторной записи, но не должны создавать два analysis run.
- Если edition удалена между подготовкой PUT и его завершением, завершение не восстанавливает её; новое издание не затрагивается. Проверить существующее поведение уборки возможного позднего orphan object и использовать текущую очередь для адресной компенсации, если она нужна.

**Не улучшать `source_uploaded`.** Клиент, получив private binding от `/local`, может заново передать целый EPUB даже для готовой редакции. Сервер должен безопасно обработать этот PUT. Не считать сам факт повторной передачи файла доказательством новой генерации.

При выключении reimport не откатывать формат новых source keys обратно к общему `owner/hash`: старые заявки очистки могут ещё выполняться. Выключатель меняет правило замены, а безопасная совместимая адресация сохраняется.

## 11. Мобильная реализация без изменения UI

### 11.1. Операция явного импорта

В точке явного импорта из Files при mobile flag=on:

1. Оставить существующее определение локального дубликата и выбор локального `book.id`. Сохранить чтение/закладки/локальные пользовательские данные; не создавать вторую карточку той же книги.
2. Подготовить SHA-256 **тех байтов, которые будут отправлены**. Сохранить нынешнюю обработку TXT/UMD и `backendOriginalSource`; не хэшировать один файл, а отправлять другой.
3. Создать UUID операции один раз. Сохранить его, исходный payload и локальную привязку операции до первого POST в существующем подходящем persisted store. Новый storage framework не нужен.
4. Явно вызвать `/local` с intent/header, обходя fast path старого backend binding для этого действия. Не вызывать перед ним `/resolve`.
5. При lost response/restart восстановить **ту же операцию**, а не создавать новый UUID.
6. После ответа сохранить выбранный binding и фазу операции до PUT, чтобы после перезапуска продолжить source upload в тот же ID.

Различать `pending registration`, `binding saved / source pending`, `completed`. Можно компактным persisted record, без отдельного большого workflow engine. Серверный ключ хранится после завершения независимо от удаления client pending record.

Повторный явный выбор файла после завершения предыдущего импорта — новая операция и новый ключ. Автоматический retry незавершённого запроса, восстановление приложения или повторный вызов одного обработчика — прежний ключ. Пока для этой локальной книги есть unresolved registration, не создавать параллельную новую операцию из-за double tap/повторного обработчика; присоединяться к текущей без нового UI.

### 11.2. Смена binding и гонки

Если вернулся тот же edition ID, не очищать готовые персонажи/сцены и пользовательские данные. Если вернулся другой ID или изменилась resolution:

- остановить старую `BackendBookSession`, запросы медиа и старые подписки;
- заменить все сохраняемые ссылки на backend identity, а не только одну переменную;
- сбросить серверные manifest/preview/analysis error/characters/media/scenes и связанные revision guards, которые относятся к старой edition;
- сохранить локальный файл, local book ID, прогресс чтения и закладки;
- передать прогресс для новой редакции штатным способом;
- игнорировать поздние publish/download callbacks старой сессии по edition/operation identity;
- запустить одну синхронизацию для новой edition.

Особенно проверить `narra-store.applyBackendManifest`: revision новой edition может быть меньше старой. Старая revision guard не должна отвергать новую разметку. Нельзя сначала сохранить новый binding, а затем применить старый manifest из незавершённого запроса.

Каталожный binding не требует `PUT /source`. Для private binding использовать текущий upload path, в том числе возможную повторную передачу EPUB. Не добавлять новую проверку наличия файла на сервере.

### 11.3. Остальные сценарии

- При mobile flag=off сохраняется нынешний поток без новых persisted import records.
- Обычное открытие/404 recovery использует прежний `/resolve` и при необходимости legacy `/local`, **без** `explicit_import`.
- Для известного результата pending import не заменять его на найденную по hash другую edition молча.
- `IMPORT_OPERATION_EXPIRED` — терминальный результат старой операции; не генерировать новый ключ автоматически. Следующий новый ручной импорт может создать новую операцию. Ошибку показывать существующим механизмом и существующим пользовательским сообщением, без нового экрана/диалога. Новые технические коды не выводить отдельными надписями в UI.
- Смена server env или mobile flag не должна превращать unresolved запрос в новый импорт. Незавершённую операцию либо безопасно завершить с прежней identity, либо остановить; отсутствие связи не означает, что сервер ничего не сделал.
- Установка приложения/Keychain не используется как «новый импорт». Для user identity пользоваться текущей авторизацией, не менять bundle ID/installation ID ради достижения тестового результата.

## 12. Коммиты, документация и review gate

Порядок работы:

1. Зафиксировать базовый SHA и перенести/закоммитить эту спецификацию.
2. Архитектор читает spec и перечисленные участки; фиксирует только конкретные противоречия. Не возвращаться к альтернативам `/resolve` vs `/local`, общей адресации и отказу от idempotency без новых фактов.
3. Разработчик реализует минимальный diff и тест-кейсы; QA параллельно готовит стенд и сценарии, но не запускает приёмку изменённого поведения до ревью.
4. **Перед выполнением тестового прогона изменений** архитектор/reviewer применяет `agentic-pr-review` к точному diff относительно base SHA. Локальная проверка diff/синтаксиса для подготовки допустима; тестовый gate и его порядок зафиксировать. На этом pre-test review не выдавать ложный `AUTO_MERGE`: execution evidence ещё нет.
5. Исправить конкретные блокирующие замечания реализации/спецификации. Ожидаемые пока отсутствующие test results не образуют вечный круг: reviewer перечисляет их как предстоящую проверку, после исправления code findings QA выполняет тесты.
6. Запустить автоматические проверки и iOS E2E, исправлять дефекты. После значимых исправлений повторить review затронутого diff и соответствующие сценарии.
7. Финальное ревью — с фактическими логами, результатами и видео. Миграция/совместимость/удаление данных означают R3 и human review перед merge; это не требует останавливать локальную реализацию или тесты ради отдельного разрешения на каждый шаг.
8. Закоммитить код, миграцию, тесты, env examples и актуализированную спецификацию/затронутые архитектурные документы. Не коммитить provider secrets, книги и большие видео.

Reviewer обязан прочитать сам skill и применимые references: data-and-compatibility, operational-risk, feature-toggles; для изменившейся архитектуры — architecture и architecture-documentation-standard. Если skill отсутствует в новом окружении, сначала найти его, затем явно сообщить об отсутствии; не обозначать обычное чтение diff как исполнение skill.

Пользователь просит коммитить **спецификацию**, реализацию и воспроизводимые тесты. ## 13. Локальный Docker-стенд

Docker разрешён пользователем. Создать отдельный Compose project, например `narra-private-reimport-qa`, отдельные volumes/порты и local-only bucket. Не выполнять `docker system prune`, не останавливать чужие контейнеры и не удалять чужие volumes.

Базовый существующий файл — `services/narra-gateway/compose.book-analysis-local.yml`. Он содержит PostgreSQL, MinIO, gateway и analysis worker. **Его недостаточно слепо запустить и считать готовым:** текущему pipeline могут потребоваться card/roster, media, scene и identity workers. В проверенном compose их нет; образцы запуска есть в `compose.i167.yml`. Добавить минимальный локальный override/QA profile с нужными существующими entrypoints и теми же кодом/образом, не поднимать production Compose со своими секретами.

- `analysis/book-analysis-worker.mjs` — analysis pipeline;
- `books/book-markup-worker.mjs` с нужными `BOOK_MARKUP_WORKER_JOB_TYPES` — cards/roster, portraits/media, scenes;
- `books/book-identity-worker.mjs` — identity, если нужен текущему сценарию;
- существующий механизм private cleanup должен реально работать на локальной БД/MinIO.

`/ABS/PATH/...` — placeholders; агент обязан подставить проверенные реальные пути и привести выполненные команды в отчёте. Не печатать resolved Compose config с секретами. `--env-file` для interpolation сам по себе не передаёт каждую env в контейнер: проверить явный mapping новой переменной, provider config и ключей во все нужные процессы.

Проверить актуальный порядок migrations/startup. Текущая команда миграции — `node db/migrate.mjs`, проверка — `node db/migrate.mjs --check`; использовать одноразовый контейнер с той же БД, если gateway требует уже применённую схему. Базовые порты compose: gateway `18787`, MinIO `19000`, console `19001`; проверить занятость и при необходимости назначить другие. Внутренние URL между контейнерами и публичные presigned media URL для Simulator должны оба работать. Логи должны позволять различить `catalog`, `legacy_reuse`, `window_reuse`, `created`, `replaced`, `idempotent_replay`, `operation_expired`. Для backend-only A-cases не изображать iOS E2E: приложить автоматический тест, вывод и соответствующий E/F case. Для GUI-failure case обязательно приложить клипы действия и восстановления в приложении. Проверить, что видео реально существует, воспроизводится, показывает нужный Simulator и не содержит секретов. SQL evidence должен быть компактным, адресным по тестовым IDs, без полного дампа пользовательской БД.

## 18. Что считать завершением

- Спецификация, минимальный код, миграция, тесты и релевантные env/docs закоммичены в изолированной ветке.
- Default mobile flag off; server env отсутствует/0 сохраняет прежнее правило регистрации; все четыре комбинации доказаны.
- UI не изменён; before/after приложение визуально использует прежние экраны и элементы.
- Каталог не заменяется; повтор до отсечки сохраняет ID/run; после отсечки создаёт новую edition и заново проходит реальный pipeline.
- Доказаны same-key replay, concurrency, rollback, crash/restart и безопасность удаления файла.
- `source_uploaded` в `/local`/`/resolve` не оптимизирован; повторный EPUB не запускает лишний pipeline.
- iOS действительно собран и подключён к локальному Docker; проверено отсутствие обращений к production gateway/data plane.
- Есть реальные E2E с обеими доступными книгами хотя бы на основном happy path; основной before/after цикл можно проводить на одной, вторую использовать для независимого smoke. Не заказывать все варианты генерации обеих книг без необходимости.
- Есть отдельные видео, остановленные на ожиданиях, и индекс доказательств; каждый обязательный case имеет PASS/FAIL/BLOCKED, нет скрытых skips.
- Pre-test и финальный review выполнены по skill. Не осталось исправимых блокирующих findings; R3 human gate на merge честно указан.
- Итоговый отчёт содержит worktree/branch/base+head SHA, коммиты, схему включения/выключения, точные команды, ссылки на видео, результаты тестов и конкретные непроверенные ограничения.

Не объявлять задачу завершённой, если реально проверен только HTTP/SQL без iOS, provider был полностью замокан, native build не выполнялся, проверка шла против production либо важные кейсы пропущены из-за отсутствующих env.

## 19. Принятые ограничения и простота решения

Транзакция БД не включает всю генерацию. Если замена уже COMMIT, а новая загрузка/LLM потом упали, прежняя разметка автоматически не возвращается. Сохраняется новая edition для корректного продолжения/ошибки. Добавление полноценного rollback на прежнюю опубликованную редакцию — отдельная задача и сюда не входит.

Поздний retry с сохранённым ключом не создаёт новую edition. Гарантия требует сохранить запись операции; временная отсечка одна её не заменяет. Отдельный source path решает другую проблему — коллизию отложенного удаления. Флаг intent решает ещё одну — отличает новое действие импорта от восстановления binding. Эти части не взаимозаменяемы.

Держать решение в пределах: один optional intent, один локальный мобильный flag, одна backend env, одна небольшая таблица результатов операций, существующая транзакционная замена и очередь cleanup, безопасный source key, адресное переключение клиентской привязки. Не менять pipeline/model policy, не добавлять UI, не делать generic orchestration/refcount/remote-flags framework и не возвращать исключённую оптимизацию `source_uploaded`.
