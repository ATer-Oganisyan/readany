# ADR-0001: Явный повторный импорт private-книги

## Контекст

Legacy `/v2/books/local` переиспользует одну private edition на пару
`(owner_subject_id, content_sha256)`. Это правильно для открытия и recovery,
но не позволяет отличить новое действие пользователя от сетевого повтора.
Кроме того, общий source key по content hash пересекается с отложенной очисткой
заменённой edition.

## Решение

- Обычный `/resolve` и `/local` без intent сохраняют прежнюю семантику.
- Явный mobile import за локальным build-time флагом отправляет
  `intent=explicit_import` и UUID в `Idempotency-Key`.
- Клиент сохраняет одну незавершённую операцию на локальную книгу и повторяет
  её с исходным payload через restart/потерю ответа.
- Gateway сериализует request key, затем `(owner, hash)`, и атомарно сохраняет
  выбранную catalog/private edition в `book_import_requests`.
- Нулевая server window только выключает замену по возрасту. Положительная
  window сравнивается с началом текущего canonical analysis по времени БД.
- Новые private sources получают key
  `books/private/{ownerSubjectId}/{bookEditionId}/source`; существующие legacy
  keys остаются на месте.

## Альтернативы

- Изменить `/resolve`: отклонено, потому что открытие книги и 404-recovery не
  являются новым действием импорта и не должны удалять готовую edition.
- Полагаться только на временное окно: отклонено, потому что потерянный ответ
  после commit может прийти на повтор уже после границы.
- Использовать Redis или отдельный сервис операций: отклонено как лишняя
  распределённая зависимость для результата одной PostgreSQL-транзакции.
- Хранить source по content hash и считать ссылки: отклонено; edition-scoped
  key устраняет коллизию с текущей очередью удаления без нового refcount.

## Последствия

Повтор одного запроса не создаёт следующую edition, точный catalog match не
создаёт private-данные, а cleanup старой edition не затрагивает новую. Замена
edition намеренно удаляет прежние server-derived данные и запускает обычный
pipeline заново; локальная книга и пользовательское состояние сохраняются.
Транзакция не охватывает последующую загрузку файла и генерацию, поэтому их
ошибки продолжаются штатными retry, без возврата удалённой edition. Добавленная
таблица и API-поля совместимы со старым приложением, но миграция, удаление
private-данных и конкурентный путь требуют human review перед merge.

## Переход

Сначала применяется additive-миграция и выкладывается backend с server window
`0`. Мобильный флаг остаётся `false`. После локальной проверки новый клиент
можно включать отдельно; положительное production-окно задаётся только
отдельным операторским решением. Откат приложения или server window к `0` не
удаляет таблицу операций и не возвращает новые source keys к legacy-формату.
