# План миграции каталожного ридера на Expo/React Native

Статус: draft для согласования
Дата: 2026-08-25
Область: книги из каталога Narra на iOS и Android

## 1. Продуктовый результат

Каталожная книга должна открываться как обычный нативный экран приложения:

```text
Тап по книге
  → один запрос на файл книги
  → первые законченные абзацы сразу появляются на экране
  → остальная книга загружается и сохраняется в фоне
```

EPUB, Foliate, WebView и локальный HTTP-сервер в этом пути не участвуют.

Целевые показатели от тапа до первого видимого текста:

| Сценарий | Цель |
|---|---:|
| Новая книга, обычная сеть | p50 до 800 мс, p95 до 1,5 с |
| Файл подготовлен заранее | p50 до 250 мс |
| Повторное открытие | p50 до 250 мс |
| Переход к следующей главе | Без видимого загрузчика |

Это целевые показатели. Их нужно подтвердить release-замерами на реальном iPhone и недорогом Android-устройстве.

## 2. Принятые архитектурные решения

1. Новый ридер делается общим кодом на Expo/React Native для iOS и Android.
2. Основной серверный сценарий — загрузка всей книги одним HTTP-запросом.
3. Если сервер отдаёт ответ потоком, клиент показывает первые абзацы до окончания загрузки всего файла.
4. Экран не зависит от транспорта: целый файл, текущие API-чанки и будущие главы подключаются через разные адаптеры.
5. Книги каталога открываются новым нативным движком.
6. Пользовательские EPUB/PDF/MOBI временно продолжают открываться текущим WebView/Foliate.
7. Первым выпускается вертикальный режим чтения. Точный постраничный режим проходит отдельный технический spike.
8. Swift/Kotlin-модуль допускается только для расчёта страниц или сложного выделения, если общий React Native-код не даст одинакового результата на обеих платформах.
9. Навигация приложения, дизайн-система и существующий reader chrome не переписываются без необходимости.

## 3. Почему текущий путь медленный

Первый чанк сейчас не отображается напрямую. До первого текста выполняется цепочка:

```text
Первый чанк
  → запись TXT
  → преобразование TXT в EPUB
  → запись EPUB и книги в базу
  → запуск WebView
  → запуск Foliate
  → разбор ZIP/EPUB
  → построение страницы
  → подключение шрифта внутри WebView
  → первый видимый текст
```

Основные точки текущей реализации:

- `packages/app-expo/src/lib/narra/backend-catalog-import.ts` — получение контента и импорт книги;
- `packages/core/src/utils/txt-to-epub.ts` — преобразование текста в EPUB;
- `packages/app-expo/src/screens/ReaderScreen.tsx` — запуск текущего ридера и WebView;
- `packages/app-expo/assets/reader/reader.template.html` — инициализация Foliate и EPUB.

Нативная миграция убирает из каталожного пути создание EPUB, ZIP-разбор, браузерный документ и мост React Native ↔ WebView.

## 4. Целевая архитектура

```text
Catalog / Library
       ↓
Reader engine router
       ├── catalog/normalized content → NativeCatalogReader
       └── EPUB/PDF/MOBI             → LegacyPublicationReader

NativeCatalogReader
       ↓
BookContentSource
       ├── FullFileSource
       ├── LegacyChunkSource
       ├── ChapterSource
       └── LocalCachedSource
       ↓
Parser / normalizer
       ↓
ReaderDocument + ReaderBlock[]
       ↓
NativeReaderSurface
       ├── текст и заголовки
       ├── изображения
       ├── таблицы
       ├── списки
       ├── ссылки и сноски
       └── reader chrome
```

### 4.1. Маршрутизация движка

При открытии книги приложение выбирает движок:

- каталожная книга с поддерживаемым контрактом → `NativeCatalogReader`;
- произвольный EPUB/PDF/MOBI → текущий WebView/Foliate;
- повреждённый или неизвестный нативный документ → управляемая ошибка или legacy fallback, если он применим.

Выбор закрывается feature flag, чтобы новый ридер можно было включать поэтапно.

### 4.2. Независимый источник содержимого

Экран работает с единым интерфейсом и не знает, как физически загружается книга.

Логические операции источника:

```ts
interface BookContentSource {
  open(bookId: string): Promise<BookManifest>;
  read(): AsyncIterable<ReaderBlock>;
  loadSection?(sectionId: string): Promise<ReaderBlock[]>;
  cacheForOffline?(): Promise<void>;
  cancel(): void;
}
```

Адаптеры:

- `FullFileSource` — один потоковый запрос всей книги;
- `LegacyChunkSource` — временная поддержка текущего `/content/chunks`;
- `ChapterSource` — прямой запрос выбранной главы по будущему контракту;
- `LocalCachedSource` — открытие без сети.

После появления backend v2 меняется адаптер, а не экран ридера.

## 5. Формат нативной книги

Ридер должен получать не HTML/CSS, а ограниченный набор смысловых блоков.

### 5.1. Манифест

```ts
interface ReaderManifest {
  contractVersion: string;
  bookId: string;
  revisionId: string;
  contentHash: string;
  language: string;
  direction: "ltr" | "rtl";
  title: string;
  author?: string;
  totalCharacters?: number;
  readingOrder: ReaderSectionRef[];
  toc: ReaderTocItem[];
  assets: ReaderAsset[];
}
```

### 5.2. Содержательные блоки

Минимальный список:

```ts
type ReaderBlock =
  | HeadingBlock
  | ParagraphBlock
  | QuoteBlock
  | ListBlock
  | ImageBlock
  | TableBlock
  | DividerBlock
  | FootnoteBlock;
```

Текстовый блок содержит ограниченные inline-стили:

- обычный текст;
- жирный;
- курсив;
- ссылка;
- ссылка на сноску;
- технический маркер персонажа или сцены, если он нужен продукту.

Произвольный CSS в нативный контракт не переносится.

### 5.3. Таблицы

Нативный контракт таблицы должен содержать:

- строки и ячейки;
- заголовочные ячейки;
- `rowSpan` и `colSpan`, если они нужны каталогу;
- выравнивание;
- текстовые блоки и ссылки внутри ячейки;
- рекомендуемые ширины столбцов.

На клиенте:

- обычная таблица строится нативными `View` и `Text`;
- широкая таблица получает горизонтальную прокрутку;
- очень сложная неподдерживаемая таблица показывает понятный fallback, а не ломает книгу.

### 5.4. Изображения и сноски

- Изображения хранятся отдельными assets с размером, MIME-типом и хешем.
- Изображение отображается через `expo-image` и кешируется.
- Сноска открывается в нативной sheet-панели.
- После закрытия сноски пользователь остаётся на прежнем месте.

## 6. Загрузка целого файла

### 6.1. Основной сценарий

1. Клиент отправляет один запрос на книгу.
2. Сервер сначала передаёт манифест, затем блоки в порядке чтения.
3. Клиент проверяет версию контракта и начинает декодировать блоки.
4. После получения первых законченных абзацев список получает данные.
5. Первый непустой `Text` появляется на экране.
6. Загрузка, индексирование и сохранение оставшейся книги продолжаются в фоне.

Для потоковой обработки сервер не должен упаковывать всю книгу в один JSON-массив, который можно разобрать только после закрывающей скобки. Подходящие варианты контракта:

- последовательность записей NDJSON;
- заголовок + length-prefixed блоки;
- простой текстовый поток для временного `normalized-text-v1`.

Конкретный формат нужно согласовать с backend-разработчиком отдельным контрактом.

### 6.2. Временная совместимость

Пока доступен только текущий `/content/chunks`, `LegacyChunkSource`:

1. получает первый API-чанк;
2. удерживает незавершённый хвост абзаца;
3. отдаёт на экран только законченные абзацы;
4. загружает продолжение в фоне;
5. не создаёт EPUB;
6. не переоткрывает ридер при добавлении текста.

## 7. Нативный экран

### 7.1. Поверхность чтения

Основной компонент — виртуализированный `FlatList`, где элементом является смысловой блок или небольшая группа связанных блоков.

Нельзя:

- помещать всю книгу в один `Text`;
- рендерить всю книгу внутри обычного `ScrollView`;
- пересобирать уже показанную часть при приходе продолжения;
- блокировать первый кадр полным поисковым индексом или записью всей книги в базу.

### 7.2. Переиспользуемые части

Сохраняются:

- верхняя панель ридера;
- нижний toolbar;
- темы и настройки;
- экран оглавления;
- reading sessions и аналитика;
- сетевые авторизация и каталог;
- TTS-плееры;
- перевод и AI-сервисы.

Меняются:

- поверхность с текстом;
- адрес позиции;
- источник текста для поиска, TTS и AI;
- механизм выделения;
- логика постраничной разбивки.

## 8. Позиции, закладки и выделения

Текущий EPUB CFI не переносится в нативный документ. Вводится общий locator:

```ts
type ReaderLocator =
  | {
      kind: "native";
      revisionId: string;
      sectionId: string;
      blockId: string;
      startOffset: number;
      endOffset?: number;
      quoteBefore?: string;
      quote?: string;
      quoteAfter?: string;
    }
  | {
      kind: "epub-cfi";
      cfi: string;
    };
```

Правила миграции:

1. Новые каталожные позиции сохраняются только как native locator.
2. Старые EPUB-записи не удаляются.
3. Во время перехода stores и сервисы принимают оба варианта.
4. Старую позицию каталожной книги переносим по прогрессу и ближайшей текстовой цитате.
5. При новой ревизии книги сначала ищем тот же `blockId`, затем цитату, затем ближайший процент.

## 9. Локальное хранение и offline-first

### 9.1. Файловый кеш

В `expo-file-system` сохраняются:

- исходный файл книги;
- изображения;
- крупные assets;
- временный незавершённый download.

Файл становится «готовым» только после проверки размера и хеша. Повреждённый кеш не открывается как валидная книга.

### 9.2. SQLite

В `expo-sqlite` сохраняются:

- манифест и ревизия;
- список секций;
- индекс блоков;
- текущая позиция;
- закладки и выделения;
- полнотекстовый поисковый индекс;
- состояние завершённой или частичной загрузки.

Запись контента и отметка о прогрессе загрузки выполняются атомарно, чтобы после падения приложения не получить «готовую» книгу с отсутствующим текстом.

### 9.3. Предзагрузка

Приоритет кеша:

1. Текущая читаемая книга.
2. Последняя открытая книга.
3. Несколько видимых карточек каталога.
4. Следующая глава открытой книги, если используется глава-ориентированный API.

Не нужно заранее скачивать весь каталог. Кеш ограничивается по размеру и очищается по LRU, кроме явно сохранённых для офлайна книг.

## 10. Поиск, TTS и AI

### 10.1. Поиск

- Индекс строится асинхронно после появления первого текста.
- Результат содержит `sectionId`, `blockId`, offset и фрагмент.
- Нажатие прокручивает `FlatList` к блоку и подсвечивает совпадение.
- Непостроенный индекс не блокирует чтение.

### 10.2. TTS

- Источником текста становятся нативные блоки, а не WebView bridge.
- Очередь строится по предложениям внутри блоков.
- Текущий locator синхронизируется с читаемым предложением.
- При переходе между секциями следующая секция подготавливается заранее.

### 10.3. Перевод и AI

- Перевод получает выделенный диапазон и текстовую цитату.
- AI-контекст формируется из блоков вокруг locator.
- Персонажи и сцены привязываются к native locator.
- Deep link из заметки или AI-ответа открывает точный блок.

## 11. Постраничный режим

Вертикальный режим реализуется полностью общим React Native-кодом.

Для постраничного режима проводится отдельный spike:

1. Измерить строки и высоту блоков.
2. Научиться делить длинный абзац между страницами.
3. Проверить изменение размера текста, полей и ориентации.
4. Проверить одинаковость iOS и Android.
5. Проверить восстановление страницы по locator.
6. Проверить выделение и TTS на границе страниц.

Если общий код устойчив, страницы отображаются горизонтальным виртуализированным списком.

Если измерения текста различаются или невозможно надёжно получить диапазоны символов, допускается маленький Expo Module:

- iOS: только расчёт строк и границ страниц;
- Android: только расчёт строк и границ страниц;
- TypeScript: единый интерфейс, экран, состояние и продуктовая логика.

Это запасной путь, а не обязательная часть первого релиза.

## 12. Этапы реализации

### Phase 0 — измерения и feature flag, 2–3 дня

- [ ] Добавить единый `openAttemptId` от тапа до первого текста.
- [ ] Измерять сеть, парсинг, первый render и снятие loader.
- [ ] Снять baseline текущего WebView в release-сборке.
- [ ] Добавить `nativeCatalogReaderEnabled`.

Критерий готовности: для каждой попытки открытия виден полный таймлайн и итоговый TTFT.

### Phase 1 — каркас второго движка, 2–3 дня

- [ ] Добавить выбор `NativeCatalogReader` / `LegacyPublicationReader`.
- [ ] Переиспользовать текущий reader chrome.
- [ ] Ввести `BookContentSource` и `ReaderDocument`.
- [ ] Добавить безопасный fallback.

Критерий готовности: тестовая каталожная книга открывает отдельный нативный экран, остальные форматы не меняются.

### Phase 2 — прямой первый текст, 3–5 дней

- [ ] Подключить текущий backend через временный адаптер.
- [ ] Удалить TXT → EPUB из нового пути.
- [ ] Показать первые законченные абзацы в `FlatList`.
- [ ] Добавлять продолжение без сброса позиции.
- [ ] Добавить пустое, ошибочное и offline-состояния.

Критерий готовности: «Золотой горшок» и другие тестовые книги показывают текст до завершения полной загрузки.

### Phase 3 — основной full-file source, 3–5 дней клиента

- [ ] Согласовать потоковый формат файла.
- [ ] Реализовать один запрос через `expo/fetch`.
- [ ] Постепенно декодировать и валидировать блоки.
- [ ] Параллельно показывать, сохранять и индексировать содержимое.
- [ ] Реализовать отмену запроса при закрытии экрана.

Критерий готовности: ридер не использует application-level чанки при наличии нового endpoint.

### Phase 4 — production scroll reader, 1–2 недели

- [ ] Темы, поля, размер и интервалы.
- [ ] Сохранение и восстановление позиции.
- [ ] Кеш и offline.
- [ ] Фоновая загрузка.
- [ ] Заголовки, списки, цитаты, изображения, таблицы и сноски.
- [ ] Accessibility и Dynamic Type в согласованных пределах.

Критерий готовности: книгу можно прочитать целиком без WebView и без скачков позиции.

### Phase 5 — backend v2 и настоящее оглавление, 2–4 недели параллельно

- [ ] Манифест, reading order и иерархический TOC.
- [ ] Стабильные section/block IDs.
- [ ] Формат смысловых блоков.
- [ ] Прямой доступ к главе как дополнительный endpoint.
- [ ] Assets с хешами и размерами.
- [ ] Версионирование и правила обновления книги.

Критерий готовности: нажатие на любой пункт оглавления открывает правильный блок, а не эвристическую главу.

### Phase 6 — продуктовый паритет, 3–5 недель

- [ ] Поиск.
- [ ] Закладки.
- [ ] Выделения и заметки.
- [ ] Копирование и перевод.
- [ ] TTS.
- [ ] AI-контекст, персонажи и сцены.
- [ ] Синхронизация позиции.
- [ ] Миграция CFI → native locator.

Критерий готовности: для каталожных книг нет продуктовой причины возвращаться в WebView.

### Phase 7 — постраничный режим, spike 1 неделя

- [ ] Реализовать и измерить общий paginator.
- [ ] Принять решение: общий React Native-код или маленький Expo Module.
- [ ] При положительном результате довести свайпы, восстановление позиции и настройки.

Критерий готовности: страницы стабильны на поддерживаемых iOS и Android при смене размеров и ориентации.

### Phase 8 — поэтапный rollout, 2 релиза

- [ ] Внутренняя сборка.
- [ ] 5% пользователей.
- [ ] 25% пользователей.
- [ ] 50% пользователей.
- [ ] 100% каталожных книг.
- [ ] После двух стабильных релизов удалить каталожную EPUB-конвертацию.

Критерий готовности: скорость, crash-free rate и доля fallback находятся в согласованных пределах.

## 13. Проверки

### Набор книг

- короткая книга;
- большая текстовая книга;
- русская классика с необычными заголовками;
- книга с изображениями;
- книга с таблицами;
- книга со сносками и внутренними ссылками;
- повреждённый и оборванный файл;
- новая ревизия уже скачанной книги.

### Сценарии

- холодный запуск;
- тёплый запуск;
- хороший Wi-Fi;
- медленная сеть;
- потеря сети во время загрузки;
- закрытие экрана во время запроса;
- убийство приложения во время записи;
- повторное открытие без сети;
- изменение темы и размера текста;
- переход по оглавлению;
- поиск и возврат назад;
- TTS через границу главы;
- обновление книги с сохранёнными закладками.

### Метрики

- tap → first byte;
- tap → first visible text;
- tap → restored position;
- количество dropped frames;
- память после открытия и после 30 минут чтения;
- CPU при скролле и TTS;
- размер кеша;
- crash-free sessions;
- доля открытий через legacy fallback.

## 14. Основные риски

| Риск | Решение |
|---|---|
| Текущий backend не содержит настоящих глав | Временный flat-text adapter, затем backend v2 |
| Старые данные завязаны на EPUB CFI | Union locator и постепенная миграция |
| Выделение через несколько блоков отличается на платформах | Отдельный spike и ограниченный первый релиз |
| Точный paginator нестабилен в общем коде | Маленький Expo Module только для layout |
| Большой файл блокирует JS-поток | Потоковый decode, небольшие batches и виртуализация |
| Повреждение partial cache | Хеши, транзакции и отдельный статус completed |
| Неподдерживаемый сложный EPUB | Legacy WebView для пользовательских файлов |
| Предзагрузка расходует слишком много трафика | Приоритеты, лимит размера и LRU |

## 15. Оценка сроков

При одном опытном мобильном разработчике и параллельной работе backend-разработчика:

| Результат | Срок от старта |
|---|---:|
| Измеряемый прототип с прямым первым текстом | 1 неделя |
| Полезный вертикальный нативный ридер | 2–3 недели |
| Production-версия каталожного ридера | 6–8 недель |
| Поиск, заметки, TTS и AI на новом locator | 8–10 недель |
| Полный постраничный режим | 10–14 недель |

Полный отказ от WebView для любых пользовательских EPUB/PDF — отдельный проект на несколько месяцев и не является условием ускорения каталога.
