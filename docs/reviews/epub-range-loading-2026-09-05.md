# Потоковое открытие EPUB: восстановление рабочего пути

## Доказанный дефект

Android при открытии EPUB сообщал `Lazy loading failed` и переходил к полной
загрузке книги. Строка 1794 текущего на момент наблюдения HTML совпадала с
`catch` в template, но не указывала на источник исключения.

Независимый запуск фактически используемого `packages/foliate-js/vendor/zip.js`
с оригинальным `01-river.epub` воспроизвёл: центральное оглавление ZIP —
7 entries; чтение `META-INF/container.xml` — `TypeError` в `getData`,
`Object.assign(z, …)` на строке 2812. `z = reader.readable` был `undefined`.

Template передавал обычный объект с `size/readUint8Array`, однако используемая
версия ZIP-парсера требует также поток `Reader.readable`. Поэтому проблема
касается любого EPUB, дошедшего до первого чтения entry через этот Range-путь,
а не только ZIP64 или повреждённых метаданных. Fallback сохранял возможность
читать, но загружал весь файл и скрывал систематически неработающий fast path.

## Узкое исправление

- Экспортирован существующий базовый `Reader` из vendored ZIP. Алгоритм ZIP и
  версия зависимости не заменены. URL-adapter наследует его настоящий stream.
- Range-loader обслуживает только EPUB. CBZ/FBZ/FB2.ZIP сразу идут через
  существующий `makeBook`, без ложной попытки разобрать их как EPUB.
- Проверяются границы запроса, HTTP 206, точный `Content-Range` и размер тела.
  Сервер без Range-поддержки по-прежнему допускает полную загрузку.
- Новое открытие отменяет предыдущие HEAD/Range/full-fetch запросы. Поздний
  результат не открывает старую книгу и не запускает её fallback; чтение
  entries закрытой/отменённой книги прекращается.

## Поведенческие проверки

Первый прогон выполнял прежний production loading block вместе с настоящим
vendored ZIP: **8 RED / 3 PASS**. После исправления и дополнения cancellation
регрессиями и проверкой full-fetch recovery — **22 PASS** в `epub-range-loader.test.ts` и
`reader-open-race.test.ts`.

ZIP-парсер и байты контейнера/главы в тесте настоящие; EPUB DOM boundary
подставлен. Архив содержит неиспользуемый member размером 2 MiB: для открытия
контейнера и выбранной главы запрашивается суммарно менее 4 KiB; весь архив не
скачивается. Это измерение конкретного локального теста, не нативная скорость
открытия и не универсальный размер оглавления ZIP.

Также проверены unsupported-format routing, сервер без Range, HTTP 200 вместо
206, неверный Content-Range, обрезанные байты, precancel, поздний ответ после
отмены, повторное destroy и смена книги во время загрузки.

## Установленный Android AFTER

CDP Network включён до открытия нового reader, а не после его готовности.
Собственная `15-large-original`: **1 719 918 bytes, 28 sections**. Реальный
production path выполнил **12 HTTP 206** с Content-Range, суммарный Content-Length
этих ответов — **74 023 bytes**; начальный HTTP 200 — HEAD, не полный GET.
В наблюдаемом открытии fallback не было, прежний CFI восстановлен. Артефакт
`ExponentAsset-7bc621c3cf02cc216d4ae01a195e7721.html` соответствует общей
ZIP/context сборке до последующего scene-availability исправления.

Источник: [native network evidence](evidence/android-2026-09-05/epub-lazy-installed-after.json),
независимо пересчитаны число и размеры Range-ответов. Это реальный app renderer,
не отдельный CLI fetch. Измерение относится к данному окну открытия, не ко всем
последующим обращениям или любому EPUB. Сопоставимое время до читаемой страницы
и release memory benchmark не измерены: процент ускорения или снижение памяти
не заявляются.
