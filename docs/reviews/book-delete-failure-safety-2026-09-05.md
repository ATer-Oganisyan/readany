# Удаление книги без потери данных при отказе

## Клиентский результат

Если БД отклоняет удаление, карточка и файл остаются доступны, а вызывающий
интерфейс получает ошибку. Массовое удаление продолжает остальные подтверждённые
ID, показывает RU/EN итог и оставляет неудачные книги выделенными для повтора.
Повторное подтверждение не запускает дубликаты. Уход с экрана не отменяет
подтверждённую пачку, но поздние callbacks и уведомления экрана подавляются.
Ошибка native Alert освобождает блокировку, следующая попытка доступна.

## Хранение и пересечения операций

- Основное удаление книги, личных записей, переписки и tombstones выполняется
  одним SQLite statement через локальную command-таблицу/trigger. Ошибка любого
  шага откатывает изменения основного файла БД. Trigger не прикреплён к books
  и не меняет семантику прямого удаления при remote sync.
- При preserveData сохраняются прогресс и личные записи; переписка удаляется
  как прежде. Hard delete теперь создаёт tombstones также для reading_sessions
  и book_tags, которые уже входят в sync whitelist.
- Чанки находятся в другой БД. Их очистка после commit не выдаётся за откат
  основной операции. Аналогично ошибка удаления cover job не возвращает уже
  успешно удалённую книгу в интерфейс.
- Файлы удаляются только после успеха основной БД. При отказе откатывается
  только invalidation этой попытки, а не предшествующее успешное удаление.
  Все повторные вызывающие одной операции получают один и тот же отказ.
- Импорт, уже записавший новый файл в БД, ждёт результат пересекающегося
  удаления до публикации/очистки. При отказе удаления новый сохранённый файл
  остаётся читаемым; при успехе импорт не возвращает книгу.
- Старый результат loadBooks не возвращает удалённую запись и не заменяет
  более новое явное восстановление. Состояние другой книги не стирается.

## Проверка, включая отклонённый кандидат

Root воспроизвёл отказ удаления, сохранение после пересечения с импортом и
три варианта запоздалой загрузки списка. Store:62 targeted PASS, независимое
ревью финальной invalidation/rollback/reload логики принято.

Первый SQLite-кандидат был отклонён root: handcrafted schema содержала
messages.updated_at, отсутствующий в приложении. Набор заменён настоящим
initDatabase() со всеми миграциями двух SQLite БД. Он дал11 RED на ошибочной
колонке. Исправление использует messages.created_at;12 настоящих SQLite-тестов
проверяют rollback, retry, soft/hard delete, другие книги, cleanup failure и
монотонные timestamps. Такой промежуточный кандидат не отправлялся в репозиторий.

UI:12 mounted-тестов, реальные RU/EN тексты и selection state. При ревью
кандидата исправлены прекращение подтверждённой пачки на unmount и зависание
lock после исключения Alert. Это не native-приёмка LibraryScreen целиком.
Для трёх новых переводов обновлён соответствующий source revision; проверки
локализации не отключались. В прежнем core-тесте Array.at заменён эквивалентным
индексированием под существующий TypeScript lib, без изменения assertions.

Итог root: mobile179 файлов/1709 PASS, core87 файлов/697 PASS, TypeScript
для app-expo и core — exit0, git diff --check PASS. Expo native-data-fetching
использован для согласования отмены, ошибки и жизненного цикла UI.

## Что ещё не принято

Новый код не прогнан на native SQLite iOS/Android. Нужен запуск актуального
JS snapshot на LOCAL Android и повторный путь импорт → чтение → удаление →
повторный импорт. Старый dev-client QA этого изменения не доказывает.

Очистка чанков/файлов после успешного commit пока best-effort, без durable
retry; это открытый риск остаточных производных данных. Не доказаны ограничение
срока зависшего запроса БД, crash/restart между двумя БД, полный multi-device
sync и поведение всех desktop adapters. Полный подписочный AI-пайп этой
итерацией не подключён; релизная готовность не объявляется.
