# Импорт и удаление: приоритет последнего действия пользователя

## Подтверждённая ошибка

Если удалить книгу во время сохранения её повторного импорта, запоздалая
операция возвращала карточку. Для обычного DELETE получалась карточка без
строки в БД: UPDATE не проверяет количество изменённых строк. При preserveData
запись действительно восстанавливалась: deletedAt: undefined очищает tombstone.
Два исходных поведенческих RED воспроизвели оба варианта.

## Изменение

- Удаление синхронно отменяет публикацию подходящих активных и ожидающих
  импортов. Время намерения фиксируется при вызове, до ожидания очереди.
- Если запись этой книги уже началась, DELETE ждёт её завершения и выполняется
  после неё. Удаление другой книги не ждёт чужой импорт или конверсию.
- Отменённый импорт не возвращает карточку и не запускает backend-обработку;
  подготовленные этой попыткой файлы очищаются.
- Последующий явный импорт после удаления остаётся допустимым восстановлением.
- Отдельный путь reimportDeletedBook использует ту же очередь и защиту от
  удаления, включая повторное удаление во время ожидания.
- Временные записи координации удаляются после завершения операции.

Root и независимое ревью расширили исходную проверку: удаление при вычислении
хеша; удаление первой книги между файлами одного batch; очередь, поставленная
до удаления; новая книга, которой ещё не было при постановке следующего импорта
в очередь. Простого запрета публикации после одного await было недостаточно.

## Границы приёмки

Root: полный mobile178 файлов/1688 PASS, полный core86 файлов/685 PASS,
TypeScript exit0, git diff --check PASS. Store targeted53 PASS у автора.
Независимый reviewer повторил53/53 PASS и принял финальный diff: исходный
blocker очереди и последующее повторное удаление закрыты.
Три явно зафиксированных RED→GREEN: исходные hard/soft гонки и повторное
удаление после новой попытки восстановления; остальные сценарии дополнительно
покрыты регрессионными тестами.

Проверяются настоящие store-операции с управляемыми задержками и файловым
адаптером в памяти. Исходные hard/soft тесты используют модель строк БД,
сверенную с реализацией UPDATE/DELETE в core. Это не нативная SQLite-проверка
и не тест внезапного завершения процесса. Новый код ещё не загружен в Android
или iOS dev-client; более ранняя нативная import-матрица проверяла другой snapshot.

На момент этой проверки оставался риск: removeBook глотает ошибку DB-delete и может
удалить файл, даже если строка в БД осталась. Тест освобождения координации
после такой ошибки не означает, что удаление при сбое хранилища работает верно.
Нужна отдельная поведенческая проверка и исправление с обратной связью в UI.
Они выполнены следующим проходом: `book-delete-failure-safety-2026-09-05.md`.
Если уже начатая запись БД не завершится, удаление той же книги будет ждать её;
эта проверка не доказывает ограниченный срок исполнения запросов SQLite.
