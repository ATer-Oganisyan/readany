# Scan: передача задания новому владельцу в PostgreSQL

Новый интеграционный тест проходит настоящие migrations, создание книги,
prepare, claim, renew и completeScan. Приложение и существующие БД не используются:
каждый запуск создаёт новую случайно именованную БД с QA-префиксом, проверяет
её отсутствие до создания и удаление после теста.

Сценарий: старый worker ожидает storage → срок lease принудительно истекает
в БД → новый владелец получает тот же job с другим token и attempts=2 →
старый heartbeat получает настоящий LEASE_LOST → storage возвращает текст.
Старый worker делает **0 модельных вызовов, 0 commit, 0 fail**.
Статус и token нового владельца не меняются. Отдельная попытка записи старым
token отвергается именно LEASE_LOST ещё до изменения стадии run.
Новый владелец сохраняет одно наблюдение и создаёт одно resolve-задание.

Автор теста и основной агент независимо запустили его на Node 24.20.0:
**1 PASS / 0 FAIL / 0 SKIP**. Основной агент усилил проверку fencing:
RUN_STATE_CHANGED после завершения нового владельца сам по себе недостаточен.
После усиления — повторно 1/1 PASS.

Полный backend с включённой новой интеграционной проверкой:
**871 PASS / 0 FAIL / 21 SKIP**, Node 24.20.0, 892 теста.
Лог `/private/tmp/narra-reclaim-backend-full.log`.
Остальные PG/S3 тесты без их environment по-прежнему пропущены;
новый тест имеет отдельный явный opt-in и собственную временную БД.

```sh
NARRA_QA_FRESH_RECLAIM_DATABASE=1 /private/tmp/node-v24.20.0-darwin-arm64/bin/node --test services/narra-gateway/test/postgres-scan-worker-reclaim.integration.test.mjs
```

Ограничения: это один процесс с настоящей PostgreSQL и двумя владельцами,
а не убийство и перезапуск двух worker-процессов. Heartbeat запускается fake
timer; истечение lease задано SQL, не ожиданием 30 секунд. Storage отложен
тестом; провайдер не вызывается. Новый владелец завершает работу через
настоящий repository, не через отдельный полный worker process.
Production-код этим дополнением не изменён. Широкая нагрузка и crash/restart
кампания остаются открытыми.

Собственная временная QA-БД вместе с синтетическими данными удаляется после
каждого запуска; для неё не создаётся резервная копия. Данные приложения не затронуты.
