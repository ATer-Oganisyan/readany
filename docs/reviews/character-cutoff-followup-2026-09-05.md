# Следующий core-loop gate: сведения о персонаже по прочитанной позиции

Подготовительный read-only разбор после исправления reader controls. Это не
реализованный контракт и не доказательство отсутствия спойлеров.

## Найденные активные пути

- `services/narra-gateway/book-catalog-service.mjs`: `publicCharacterTraits`
  выбирает последний snapshot; `analysisCharacterProfile` возвращает финальные
  role/description/speech/greeting. `v3Manifest` не ограничивает профиль cutoff.
- `packages/app-expo/src/lib/narra/backend-book-contract.ts`:
  `backendConfirmedCharacters` игнорирует `_progress`,
  выбирает максимальный cutoff; `backendVisibleProfileDetails` накладывает final поля.
- `ReaderCharacterCard.tsx` показывает эти biography/traits.
- `NarraCharacterChatScreen.tsx`: system prompt содержит final traits/role/style;
  память и история также передаются. Готовый greeting попадает в историю напрямую.
- `lib/ai/narra-chat.ts` → generic `POST /v2/ai/chat/complete`: сообщения без
  edition/character/cutoff; сервер не выбирает позиционно-безопасный профиль.
- `postgres-book-markup-repository.mjs`: progress хранится через `GREATEST`,
  то есть максимальная достигнутая, а не текущая позиция после возврата назад.

## Требуемый результат, не упрощать до пустых профилей

До позднего события карточка и разговор должны использовать содержательный
профиль из уже прочитанных подтверждённых фактов. После события профиль может
дополниться. Нельзя просто скрыть все био/речь до конца книги: это лишит раннее
общение смысла и не соответствует целевому core loop.

Нужны привязанные к edition/contentHash нормализованный cutoff и публикация;
выбор snapshot не позднее cutoff без fallback к финальному; позиционно
обоснованные описание, роль, речь, greeting. Смешанные ранние/поздние свободные
описания нельзя выдавать как ранние — требуется безопасная содержательная
проекция из evidence или отдельная позиционная генерация. Различать текущую
позицию и максимальную прочитанную; политику знания при rewind сформулировать
до изменения хранения прогресса.

Клиент не должен восстанавливать final поля из кэша. Серверный character-chat
должен получать identity/cutoff и выбирать профиль; память, greeting и история
не должны обходить ограничение. Проверить старые кэши и холодное восстановление.

## Приёмка следующего изменения

Собственный персонаж с ранним фактом и поздним секретом. Actual catalog service →
мобильный mapper/card → захваченный HTTP chat body: ранний профиль остаётся
полезным, но позднего секрета нет ни в одном поле или prompt. После границы
поздний факт появляется. Проверить rewind, старую память/историю и cold restore.
Известные backend-book-contract tests сейчас закрепляют показ будущей черты и
секрета при раннем прогрессе; заменить их только после явного нового контракта.
`progressive-personality.test.mjs` проверяет canonical snapshots, но не весь
публичный путь. `character-reading-context.test.ts` ограничивает цитату страницы,
не весь профиль. Все перечисленные проверки сквозного результата ещё предстоят.
