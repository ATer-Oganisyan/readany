# Сохранение конечной публикации в staged QA

Проблема: короткий staged-прогон сохранял ответы модели, но не финальный нормализованный профиль и опубликованную разметку. После очистки собственных строк БД нельзя было независимо проверить, что реально получит клиент. Файл сохранялся только для multi-chunk.

Исправление: любой staged-прогон сохраняет `pipeline-evidence.json` перед проверками публикации и семантики. Файл создаётся исключительно новым, с правами 0600, содержит исходный SHA, run ID, наблюдения, профили, публикации и разметку. Разрешения на вызовы моделей, approval и шлюз не изменены.

Поведенческая регрессия использует настоящие workers, локальный HTTP и PostgreSQL; ответы модели — mock. На свежей `narra_qa_pipeline_20260905_evidence_red01` новый тест упал именно из-за отсутствующего файла. После исправления на отдельной свежей `narra_qa_pipeline_20260905_evidence_green01` прошли 6/6 тестов, без пропусков. Проверены доступность артефакта после возврата/очистки, права 0600, идентичность исходника/run, профиль, публикация, разметка и четыре вызова. Команда: `QA_STAGE_MOCK=true` с явными `QA_DB_URL`/`QA_DB_CONFIRM`, Node24, `node --test scripts/qa/book-analysis-pipeline-canary.test.mjs`.

Это улучшение достоверности QA, не исправление качества персонажа. Предыдущий живой прогон не получает задним числом доказательства правильного конечного голоса: для него по-прежнему сохранены только исходные ответы и результаты проверок. Ошибка worker до сбора публикации также не гарантирует этот файл; отдельные ответы staged остаются отдельными артефактами.
