# Core product loop NARRA: архитектура и причины ожиданий

Дата: 5 сентября 2026. Диагностика текущего локального рабочего дерева
`mishanaer/Narra`, а не утверждение о конфигурации запущенного TEST.
Поведение приложения и backend в этом проходе не изменялось.

## Главный вывод

Локальное чтение и серверный AI уже разделены, но интерактивные функции
опираются на тяжёлую обработку всей книги и несколько несогласованных
контрактов. Нельзя исправить все наблюдаемые проблемы одной заменой модели:
есть отдельные причины в очередях, публикации результатов, выборе контекста,
промптах и стартовой позиции TTS.

Подтверждено чтением активных call sites и целевыми проверками. Live задержки,
качество генераций и конкретный native эпизод неправильного старта TTS в этом
проходе не измерены. TEST `/health` повторно вернул HTTP 502 примерно за
0,14 s; тело — HTML nginx, не JSON отказа провайдера.

## 1. Девять основных клиентских сценариев

| № | Действия читателя | Правильный продуктовый результат | Текущая реализация / граница |
| --- | --- | --- | --- |
| 1 | Library → Files/ссылка → собственная книга → открыть | Читать сразу после надёжного локального сохранения; AI готовится отдельно | Локальная валидация, преобразование, файл и БД; затем backend binding/upload и фоновая сессия. Её старт после импорта не должен блокировать читалку |
| 2 | Каталог → выбрать книгу → скачать → открыть | Переиспользовать готовый анализ точного издания | `bookEditionId` и серверная публикация позволяют не анализировать заново. Готовность конкретной каталоговой книги надо проверять, а не предполагать |
| 3 | Чтение → листание/TOC/настройки → закрытие/возврат | Плавный текст и точное сохранение места независимо от AI | Foliate в WebView, локальные CFI/прогресс/checkpoint; backend получает прогресс отдельно. Последний native аудит принят в описанных границах |
| 4 | Встретить героя → имя/список → карточка | Только уже встреченные герои; понятное различие предварительного имени, готового профиля и медиа | Во время scan возможны provisional names. Полноценные персонажи применяются клиентом при `availability=ready`; картинки и другие медиа имеют отдельную готовность |
| 5 | Карточка → разговор с героем → назад в книгу | Узнаваемый характер, точные знания о прочитанном, короткий живой ответ | Отдельный non-streaming chat: role/traits/speechStyle, до 18 сообщений, память и совпавшая видимая страница. Это не retrieval-agent всей книги |
| 6 | Narra → вопрос о странице/главе/книге → источник → чтение | Ответ опирается на нужную книгу и прочитанный контекст; поиск не выглядит зависанием | Streaming reading-agent с инструментами. Server index → local index/original-file fallback. Общий чат без выбранной книги и BookChat — разные контексты |
| 7 | Слот в читалке или выделение → нарисовать → вернуться | Предсказуемая сцена нужного момента; можно продолжать читать, не запускать дубли | Сейчас два разных pipeline: inline server job по progress и отдельный экран с прямым запросом изображения по excerpt. Контекст, ожидания и формат отличаются |
| 8 | «Озвучить» страницу/выделение → пауза/продолжение → следующая глава | Начало слышимого текста соответствует понятному пользователю правилу; голос и подсветка следуют очереди | DOM → предложения/CFI → клиентский voice plan → Gateway/SaluteSpeech → TrackPlayer. Кнопка читалки запускает текущую страницу, Play в плеере возобновляет очередь |
| 9 | Выделение → заметка → другая страница → заметка → возврат/перезапуск | Сохранённая запись ведёт к своему месту и своей книге, без копий Reader | Повторные переходы и book scope исправлены в предыдущем проходе; PDF якорь имеет точность страницы, не диапазона слова |

Критический цикл: **импорт → чтение → контекстное взаимодействие → то же
место чтения → сохранённое продолжение**. Анализ всей книги — вспомогательная
работа, а не действие, завершения которого должен ждать читатель.

## 2. Как соединены клиент и backend

```text
Файл / каталог
 ├─ локальный файл + БД → Foliate/WebView → CFI/checkpoint → чтение
 └─ Gateway: installation identity + binding точного издания
     ├─ PostgreSQL: книги, позиции, analysis runs/jobs, факты, публикации
     ├─ S3/MinIO: исходник, нормализованный текст, generation cache, медиа
     └─ prepare → scan всех чанков → resolve → synthesize → validate → publish
                                                     ├─ профили для клиента
                                                     ├─ отдельные media jobs
                                                     └─ отдельная TTS-разметка

Чат персонажа → Gateway complete → LLM
Narra → клиентский reading-agent ↔ инструменты поиска → Gateway stream → LLM
Inline сцена → PostgreSQL scene job → worker → Gateway image provider → S3
Сцена выделения → Gateway /media/images → результат в локальный файл
Озвучка → локальные предложения → Gateway speech → TrackPlayer
```

Очереди анализа в PostgreSQL используют lease, heartbeat, `SKIP LOCKED`,
ограничение попыток и идемпотентные ключи. Это полезная основа надёжности.
При этом некоторые gateway-журналы/ограничители локальны процессу: текущую
архитектуру нельзя объявлять готовой к произвольному горизонтальному
масштабированию gateway.

В репозитории есть legacy markup и external pipeline. По умолчанию выбран
`narra`; описание ниже относится к нему. Нельзя судить о работающем пути
по одному старому имени файла или комментарию.

Источники: [pipeline](../../services/narra-gateway/book-analysis-pipeline.mjs),

## 3. Чанкирование и длительная разметка

### Аналитические чанки

После подготовки получается нормализованный текст с секциями и координатами.
Текущие значения по умолчанию:

- Целевое ядро — 4 000 UTF-16 code units; минимум 2 500, максимум 5 000.
- Контекст — ещё до 500 с каждой стороны.
- Ядра покрывают текст ровно один раз; соседний контекст перекрывается.
- Разрез подбирается около целевого размера по границам секций, абзацев,
  предложений и строк. Жёсткое правило «одна глава = один чанк» отсутствует.
- Есть hash, детерминированная идентичность внутри run и отдельные UTF-8
  byte offsets для Range-чтения объекта. Это не chunking по токенам модели.

Контрольный запуск настоящего chunker на синтетическом русском тексте:

| Объём текста | Чанков | Суммарный контекст всех чанков |
| --- | --- | --- |
| 100 000 | 25 | 124 000 |
| 500 000 | 125 | 624 000 |
| 1 000 000 | 250 | 1 249 000 |

Это иллюстрация объёма работы, не benchmark живой модели. Перекрытие в этом
примере добавляет около 25% текста; поверх него повторяется большой scan prompt.

### Почему это долго

1. На каждый чанк приходится отдельный LLM scan. Он извлекает упоминания,
   действия, реплики, черты, внешность, события, места и отношения с цитатами.
2. Balanced policy делает одну semantic attempt по умолчанию. Неподтверждённый
   или пустой результат может вызвать adaptive split: исходный запрос плюс
   два меньших. Технические job retries — отдельный механизм.
3. `resolve` начинается только после готовности всех обязательных scan jobs.
   Один проблемный хвост задерживает следующую стадию всей книги.
4. После разрешения имён выбирается до 20 подтверждённых героев по частоте
   упоминаний/доказательств. Это осознанный лимит, а не обещание показать всех.
5. Для каждого героя текущий synthesis выполняет минимум три последовательных
   LLM-запроса: основной профиль → дополнительный поиск черт → строгий аудит.
6. Непринятая/слишком большая personality timeline вызывает дополнительные
   последовательные запросы по контрольным точкам.
7. Общая сборка ждёт необходимые профили; затем validate и publish.

В checked-in compose по умолчанию **одна scan replica и одна synthesize
replica**; каждый runner ждёт `runOnce()` перед следующим заданием. Возможность
параллельной обработки в БД не означает, что реальные реплики её используют.
Фактическое число процессов на TEST сейчас неизвестно.

Полезная модель времени:

`T готовности ≈ prepare + очередь + scan(N, concurrency) + resolve +
synthesis(K, calls/character, concurrency) + validate + publish`.

Previews уже существуют, но дают предварительные имена, а не полноценный
доказательный диалог по частично готовой книге. Клиент обычно обновляет
manifest примерно раз в 5 s; после сетевых ошибок интервал растёт до 60 s.
Это добавляет время обнаружения результата, но не объясняет само по себе
много минут вычислений.

## 4. Персонажи: качество анализа и качество разговора — разные вещи

Сильная сторона backend: факты проверяются по реальным цитатам и координатам;
идентичности объединяются отдельно; профиль имеет evidence и confidence.
Для синтеза выбирается разнообразная доказательная выборка: до 240 наблюдений
и 48 000 bytes. Нельзя просто убрать эти проверки ради быстрого ответа.

Но найдены конкретные разрывы:

- **Считается история развития характера, публикуется финальное состояние.**
  `analysisCharacterProfile` намеренно берёт последний personality snapshot.
  Это не профиль «на текущем месте чтения». Промпт чата отдельно запрещает
  спойлеры, но уже получает итоговые черты. Архитектурный конфликт подтверждён;
  конкретная утечка будущего сюжетного факта в live ответе не воспроизводилась.
- **В разговор попадает не весь подготовленный профиль.** System prompt
  использует имя, роль, traits и speechStyle, но не передаёт description,
  speechExamples и доказательные события/отношения как отдельный контекст.
  Поэтому дорогая разметка не полностью превращается в качество роли.
- **У героя нет retrieval-поиска фактов книги.** Есть до 18 сообщений,
  память до 900 символов и видимая страница до 4 000 символов. Страница
  добавляется только при точном совпадении книги и CFI; иначе она отсутствует.
  Вопрос о более раннем эпизоде может остаться без нужных доказательств.
- **Ответ не стримится.** `/chat/complete` возвращает весь текст; читатель
  видит ожидание до полного завершения. Клиентский бюджет — 60 s, upstream
  complete имеет 120 s на provider attempt: таймаут клиента может наступить раньше.
- На первом открытии возможны дополнительные запросы для приветствия и даже
  склонения имени в placeholder. Память обновляется в фоне через четыре
  сообщения; это тоже нагрузка на общий LLM gate.

Источники: [публичный профиль](../../services/narra-gateway/book-catalog-service.mjs),
[чат и system prompt](../../packages/app-expo/src/screens/NarraCharacterChatScreen.tsx),

## 5. Почему может тормозить Narra

Narra — другой путь: клиентский LangGraph reading-agent с поиском и
streaming-ответом. Инструменты ограничены, повторные вызовы дедуплицируются;
отдельный tool имеет бюджет 45 s, граф — до 18–24 шагов в зависимости от задачи.
Это число шагов графа, не столько обязательных LLM-запросов.

Подтверждённые источники задержки и ненадёжного контекста:

1. `index-first` выбирается уже при наличии `bookEditionId`, а не после
   подтверждения готовности индекса. Backend search по умолчанию выключен,
   а постановка индекса на обработку сделана явной операторской операцией.
   Поэтому импортированная книга не гарантированно получает рабочий RAG.
2. Search действительно имеет fallback на локальный индекс/исходный файл.
   Но сначала может ждать неработающий server path. Empty successful results
   сами по себе не вызывают этот fallback — он находится в catch.
3. Перед основным ответом `await maybeCompressThreadMemory()` может добавить
   отдельный LLM-вызов. Сжатие памяти стоит на критическом пути и не получает
   signal основной streaming-сессии через этот интерфейс.
4. Разметка, synthesis, Narra, герой и вспомогательные запросы используют
   **один FIFO `llmGate`**, по умолчанию 12 активных запросов. Отдельного
   приоритета/резерва для пользовательского разговора нет. Работа gate
   подтверждена маленьким исполненным FIFO-опытом, не production load test.
5. Tool timeout возвращает управление через Promise.race, но сам по себе
   не отменяет нижележащую операцию. Это важно для запоздалого fallback.

Результаты стрима публикуются в React примерно раз в 160 ms. Такая частота
может влиять на ощущение набора текста, но не является основной гипотезой
для минутного ожидания перед первым ответом.

## 6. Сцены: два реально используемых pipeline

| Свойство | Inline слот в читалке | «Нарисовать» выделенный фрагмент |
| --- | --- | --- |
| Вход | `progress_fraction` + edition | Реально выделенный excerpt, глава, метаданные, герои |
| API | `/v2/books/:id/scenes/at` | `/v2/media/images` |
| Зависимость от анализа | Требуется ready publication | Этот путь не имеет такой же ready-проверки |
| Контекст | До 500 символов перед вычисленным text offset | Excerpt в промпте до 1 200 символов, предыдущие сцены и метаданные |
| Промпт | Серверный бюджет 950 символов; excerpt сжимается одним из первых | Клиентский ориентир 2 500, hard limit 4 000 |
| Картинка | Provider request 4:3 | Запрос 1024×1024 → 1:1 |
| Выполнение | PostgreSQL job + отдельный scene worker + polling + download | Прямой запрос и локальное сохранение; catch запускает другой image path |
| Восстановление | Есть server identity результата и сохранённый intent | Нет такого же долговечного server job ID в этом call path |

Что это означает для пользователя:

- Две кнопки с близким смыслом способны дать разные качество, кадрирование
  и время ожидания. Это подтверждённое расхождение, не предположение о модели.
- Inline координата сейчас вычисляется как `round(progress * normalizedLength)`.
  Клиент не отправляет точный текстовый якорь/цитату в этом запросе. Равенство
  reader fraction и доли нормализованных символов не доказано; отсюда риск
  иллюстрировать соседний эпизод. Конкретное смещение надо измерять на книге.
- Inline generator читает и проверяет hash **всего нормализованного объекта**,
  а затем вырезает 500 символов. Это лишний I/O на каждую uncached сцену,
  в отличие от Range-чтения scan-чанков. Доля I/O в live latency неизвестна.
- В inline prompt не передаются глава, предыдущие сцены и явный жанр из
  клиента: соответствующие поля заполняются пустыми. У выделения они есть.
- Поиск героев в обоих scene prompts основан на буквальном вхождении имени,
  не на полноценном общем морфологическом matcher: падежная форма может
  оставить нужный паспорт внешности вне промпта.
- Inline клиент ограничен 5 минутами, внутренний endpoint — 10 минутами;
  checked-in worker timeout тоже 10 минут. Image provider default — 15 минут,
  но внутренний лимит может оборвать его раньше. Отдельный legacy scene-job
  runner имеет 15-минутную попытку: это **не** тот же PostgreSQL worker.
- Экран выделенной сцены использует старый request lifecycle: 150 s до
  завершения fetch/headers, без общего body deadline в этом call path.
  После любой ошибки primary вызывается fallback; уход с экрана не передаёт
  signal отмены генератору изображения. Очистка screen effect относится к audio.

В checked-in compose scene worker вынесен в профиль `scenes`, одна replica
по умолчанию; стандартный deploy script включает этот профиль. Нельзя
утверждать, что на TEST worker отсутствует, пока не проверены процессы и очередь.

## 7. Озвучка: откуда берётся странный старт

Нажатие в читалке вызывает `startPageTTS()`. Оно намеренно не передаёт
`currentCfi` в первый запрос `getNormalizedVisibleTTSSegments()`, чтобы не
использовать отстающий CFI после быстрого листания. Поэтому начальный путь
идёт через геометрию видимых предложений, а не через точный relocation range.

**Подтверждённая особенность алгоритма:** `isRangeStartVisibleInReader`
проверяет первый прямоугольник всего предложения. Если предложение началось
на предыдущей странице, а его продолжение видно сейчас, оно отбрасывается.
Озвучка может начать со следующего предложения, пропустив видимый хвост.
Контрольный запуск настоящих функций из template дал:

```text
Предложение пересекает видимую область: true
Предложение принято как стартовое:      false
```

Геометрия в опыте контролируемая, не настоящее устройство. Это доказывает
решение алгоритма, но не устанавливает, какой именно дефект пользователь
наблюдал на своей странице.

Другие факторы:

- WebView ждёт до 3 s появления content/overlayer, но это не гарантия, что
  закончилась именно последняя навигация. При неготовых сегментах есть
  fallback на visibleText, уже с менее точными CFI.
- `startPageTTS` до `ttsPlay` ожидает контекст и иногда следующую главу.
  В этом async участке не виден единый request-generation/cancel guard,
  привязанный к свежему положению страницы. Гонка при листании/повторном tap —
  кандидат на отдельное native воспроизведение, пока не принятый диагноз.
- Кнопка читалки заново стартует страницу; Play в плеере продолжает старую
  очередь; выделение читает выделенный текст. Разные намерения недостаточно
  явно обозначены одной общей формулировкой «озвучить».
- Первый звук ждёт буфер до **8 сегментов** при **3 одновременных запросах**.
  Значит, задержка до звука зависит не только от первого синтеза. Медленный
  ранний сегмент задерживает упорядоченную очередь.
- Для reader TTS голос выбирается клиентской эвристикой по репликам,
  речевым глаголам и ближайшим именам. Backend имеет отдельный source-bound
  TTS script с атрибуцией реплик, но вызова его потребления в исследованном
  мобильном reader path не найдено. Он не определяет стартовую точку читалки.
- Backend TTS script строится после publication, группирует речь примерно
  по 5 000 символов с контекстом 500 и обрабатывает requests последовательно.
  Это отдельная разметка, не аудиобуфер по предложениям.

## 8. Как измерять скорость и что менять первым

Не смешивать следующие времена:

| Метрика | Границы |
| --- | --- |
| Импорт → можно читать | Tap/import start → видимый доступный текст |
| Page turn | Tap/swipe → стабильная новая страница и CFI |
| Первый полезный герой | Начало импорта → доказательный доступный профиль уже встреченного героя |
| Полная разметка | Run enqueue → published; отдельно queue/scan/resolve/synthesis/validation |
| Ответ персонажа/Narra | Send → первый полезный текст; отдельно retrieval, memory и provider |
| Сцена | Tap → job accepted → provider complete → download → картинка в WebView |
| Озвучка | Tap → зафиксированное стартовое предложение → первый слышимый звук |

Для каждого нужны p50/p95, ошибки/повторы, тип книги, объём, cold/cache hit,
конфигурация worker/model и нагрузка. Старый Android опыт 74 023 bytes для
открытия EPUB 1 719 918 bytes доказывает частичное чтение архива, не скорость
AI и не latency от нажатия. Снижение render counts тоже не равно FPS.

Приоритет предлагаемых изменений, без реализации в этом проходе:

1. Зафиксировать единый контракт позиции: edition/content hash + section +
   точный anchor/CFI + excerpt. Отдельно хранить текущую позицию и максимально
   прочитанное. На нём согласовать TTS, сцены и контекст персонажа.
2. Воспроизвести TTS на странице с переходящим предложением и быстрой
   навигацией. Выбрать явные действия «с видимого места», «продолжить»,
   «выделение»; не угадывать намерение по глобальному play state.
3. Отделить интерактивную очередь от bulk analysis, дать пользовательским
   ответам резерв; не просто увеличивать число scan workers до упора.
4. Ввести полезную раннюю публикацию профилей по прочитанным доказательствам;
   полную глобальную сверку продолжать в фоне с версионированием identity.
   Не ослаблять проверку цитат и не выдавать provisional за достоверный факт.
5. Передавать в character chat доказательные факты и примеры речи до нужной
   границы, добавить ограниченный retrieval, стримить ответ; согласовать
   финальный профиль и обещание «без спойлеров».
6. Объединить два scene pipeline в один долговечный job-контракт: одинаковый
   anchor/context/prompt policy/aspect ratio/cancel/retry/deadline. Не держать
   длинную image generation на коротком клиентском HTTP ожидании.
7. Для Narra проверять готовность индекса, автоматически запускать нужную
   индексацию и убрать сжатие памяти с критического пути текущего ответа.
8. Уменьшать TTS initial buffer и менять параллелизм только после замеров
   first-audio и underrun на реальных сетях; не менять вслепую 8 на 1.

## 10. Можно ли заменить TEST API своим ключом

Адрес backend и ключ AI-провайдера — разные сущности. Новый ключ можно
настроить **на рабочем Gateway**, если соответствующий provider route
поддерживается. Он не заменяет PostgreSQL, object storage, queues/workers,
installation identity и book API. HTML 502 от nginx на `/health` не является
доказательством неверного AI-ключа: точная причина требует доступа к upstream
процессу и его логам.

Практические варианты: восстановить существующий TEST либо поднять полноценный
второй/local backend и переключить клиент на его URL. Ключ хранить только
серверно, не в `EXPO_PUBLIC_*`, git или переписке. Пока достаточно сообщить
название провайдера; доступы и конфигурацию нужно подключать отдельным
безопасным шагом. Никаких ключей в ходе диагностики не запрашивалось и не менялось.
