# Оценка скорости разметки книг

Документ описывает оценочную модель для pipeline `prepare → scan → resolve → synthesize → validate → publish`.

## Обозначения

- `N` — количество книг, одновременно находящихся в очереди.
- `P` — среднее количество страниц в книге.
- `S` — среднее количество символов на странице, включая пробелы.
- `L = P × S` — средний размер нормализованного текста книги в символах.
- `C` — целевой размер core-части scan-чанка. Текущее значение: `4000` символов.
- `J = ceil(L / C)` — приблизительное количество scan-заданий на книгу.
- `W_scan` — фактическое количество scan-воркеров.
- `t_scan` — среднее время обработки одного scan-чанка в секундах.
- `q_scan` — коэффициент дополнительных вызовов из-за повторов и split-обработки.
- `K` — среднее число выбранных для публикации персонажей в книге.
- `W_synth` — количество synthesize-воркеров.
- `t_profile` — среднее время синтеза одного профиля персонажа.

Pipeline работает с символами, а не с издательскими страницами. Если точный размер текста неизвестен, для обычной прозы можно использовать `S = 1800–2000` символов на страницу. Сноски, иллюстрации, стихи, пьесы и сложная FB2-разметка могут заметно изменить это отношение.

## Количество scan-заданий

Для одной книги:

```text
L = P × S
J = ceil(L / C)
```

Для партии книг разного размера:

```text
J_total = sum(ceil(L_i / C))
```

Для `N` примерно одинаковых книг:

```text
J_total ≈ N × ceil(L_avg / C)
```

Overlap расширяет контекст модельного запроса, но не должен прибавляться к размеру книги при расчёте количества core-чанков.

## Пропускная способность scan

Если используется уже измеренное полное время чанка, включающее реальные повторы и split-запросы:

```text
V_scan_chunks_per_second = W_scan_effective / t_scan

T_scan_seconds = J_total × t_scan / W_scan_effective
```

Эквивалентно, в минутах:

```text
T_scan_minutes =
    N × ceil(L_avg / C) × t_scan
    ────────────────────────────
              60 × W_scan_effective
```

Формула для Excel или Google Sheets:

```text
=N*ROUNDUP(L_avg/C,0)*t_scan/(60*W_scan_effective)
```

Если `t_scan` взято для одного чистого LLM-вызова, нужно учитывать повторы отдельно:

```text
T_scan_seconds = J_total × t_scan × q_scan / W_scan_effective
```

Для режима `full → split into two halves` приближённая оценка числа вызовов:

```text
q_scan ≈ 1 + 2 × p_split + average_retry_calls
```

Где `p_split` — доля чанков, для которых после полного запроса потребовались ещё два запроса половин.

Фактический параллелизм ограничивается не только контейнерами:

```text
W_scan_effective = min(
    W_scan,
    provider_concurrency,
    rate_limit_equivalent_concurrency
)
```

После достижения лимита LiteLLM/OpenRouter увеличение числа контейнеров перестаёт линейно ускорять обработку.

## Скорость в книгах в час

Для книг среднего размера:

```text
books_per_hour =
    3600 × W_scan_effective
    ─────────────────────────────
    ceil(L_avg / C) × t_scan
```

Это пропускная способность потока. Она не равна времени ожидания конкретной книги. Текущий планировщик распределяет scan-задания между активными run достаточно равномерно, поэтому несколько одинаковых книг обычно достигают конца scan примерно вместе — ближе ко времени обработки всей партии.

## Полное время разметки

Для одной книги:

```text
T_full =
    T_queue +
    T_prepare +
    T_scan +
    T_resolve +
    T_synthesize +
    T_validate +
    T_publish
```

На стадии synthesize создаётся одно модельное задание для каждого выбранного персонажа и одно быстрое задание сборки книги:

```text
J_synth_per_book ≈ K + 1

T_synthesize_batch_minutes ≈
    N × K × t_profile
    ──────────────────
       60 × W_synth_effective
```

Для партии одинаковых книг консервативная оценка времени последней книги:

```text
T_last_book ≈
    T_scan_batch +
    T_resolve_batch +
    T_synthesize_batch +
    T_validate_and_publish
```

Часть стадий может выполняться параллельно: synthesize небольшой книги может начаться, пока scan больших книг ещё продолжается. Поэтому сумма выше — плановая оценка с запасом, а не строгая нижняя граница.

## Текущий замер TEST

Базовый замер на четырёх scan-воркерах, выборка 65 завершённых scan-заданий:

- среднее `t_scan = 27,4` секунды;
- медиана `31,8` секунды;
- p90 `39,4` секунды;
- ошибок в выборке: `0`;
- фактическая скорость: около `8,76` чанка в минуту или `525` чанков в час.

После масштабирования TEST до `8 scan + 4 synthesize`, первая выборка из 37 завершённых scan-заданий:

- `W_scan = 8`;
- среднее `t_scan = 26,3` секунды;
- медиана `32,3` секунды;
- p90 `39,4` секунды;
- ошибок в выборке: `0`;
- расчётная скорость: около `18,25` чанка в минуту или `1095` чанков в час.

Для планирования безопаснее использовать `t_scan = 30–35` секунд, пока не накоплена более длинная выборка.

Исторические медианы завершённых `book-analysis-v51` на TEST:

- prepare: `1` секунда;
- resolve: `36` секунд;
- synthesize: `10,7` минуты на книгу;
- validate: `1` секунда;
- publish: `1` секунда.

Synthesize сильнее зависит от числа персонажей и очереди: исторический p90 стадии составляет около `52,6` минуты.

## Пример: 10 книг по 200 страниц

Центральное допущение: `1800` символов на страницу.

```text
N = 10
P = 200
S = 1800
L = 200 × 1800 = 360 000 символов на книгу
J = ceil(360 000 / 4000) = 90 чанков на книгу
J_total = 10 × 90 = 900 чанков
```

Scan по текущему измеренному среднему после масштабирования до восьми воркеров:

```text
T_scan = 900 × 26,3 / 8 / 60
       ≈ 49 минут
```

Плановый диапазон при `30–35` секундах на чанк:

```text
900 × 30 / 8 / 60 = 56,25 минуты
900 × 35 / 8 / 60 = 65,63 минуты
```

То есть для scan следует планировать примерно `55 минут — 1 час 10 минут`.

Если средняя страница содержит `2000` символов, получится 100 чанков на книгу и 1000 на партию:

```text
T_scan = 1000 × 26,3 / 8 / 60
       ≈ 55 минут
```

При четырёх synthesize-воркерах и исторической медиане `10,7` минуты на книгу партия требует около `27` минут synthesize-работы при близком к линейному масштабировании. С учётом resolve, конкуренции за LLM и запаса полное завершение всех десяти книг оценивается примерно в `1 час 20 минут — 1 час 50 минут`. Первые книги могут завершиться раньше за счёт перекрытия стадий.

## Практическая формула для прогноза оставшейся очереди

Когда известны реальные счётчики заданий, оценка точнее расчёта через страницы:

```text
T_remaining_scan_minutes =
    (queued_scan_jobs + running_scan_jobs) × t_scan
    ──────────────────────────────────────────────
                   60 × W_scan_effective
```

Пересчитывать прогноз следует при изменении числа воркеров, scan policy, модели, лимитов провайдера или заметном изменении p50/p90 времени чанка.
